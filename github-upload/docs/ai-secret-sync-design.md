# AIキーの暗号化同期（ロードマップ B）設計書

対象: `docs/ROADMAP-2026-07.md` の「B. APIキーの暗号化同期」。
前提: V2同期 Phase 2 完了（`docs/sync-v2-phase2-plan.md`）。

この設計書は第3版である。Advisorレビューを二度受けて、脅威モデルを二度書き直した。
初版の「サーバーは復号できない」も、第2版の「認証を作り替えれば運営からも守れる」も
誤りだった。経緯は2章に残す。

## 1. 目的と非目的

**目的**: 端末を増やすたびに Gemini / Groq のAPIキーを貼り直す手間をなくす。

**非目的**:

- サーバー側でAIを代行すること（それは ROADMAP の E）。
- キーの管理機能（世代・失効・共有）。ここで扱うのは「同じ人の同じ部屋の端末間で持ち回る」ことだけ。
- legacy同期への対応。legacyには鍵素材がないため、機能自体を出さない。
- **アプリを配信する運営からキーを隠すこと**（2章。同一オリジンのPWAでは暗号で解けない）。

## 2. 脅威モデル

### 2.1 二度の訂正の経緯

この章は二度書き直している。記録として残す。

**初版**は「鍵は V2 secret から派生する。サーバーはHMACハッシュしか持たないため、
D1を覗いても復号不可」と書いた。前半は正しいが、そこから「サーバーは復号できない」と
結論したのが誤りだった。V2の通信では room secret を `x-room-key` ヘッダで**毎回サーバーへ
送っている**（`syncHeaders()`）。リクエストを処理する時点では secret の平文がサーバー上に
あるため、Function を書き換えられる／ログを取れる運用者は同じ HKDF で封筒を開ける。

**第2版**はこれを受けて「運営は技術的に読み取れます」と正直に書く方針にした。
同時に、認証を capability 分離へ作り替えれば運営からも守れると考えた
（`docs/sync-auth-v3-design.md`）。これも誤りだった。理由は3つあり、詳細は同文書にあるが、
決定的なのは**同一オリジンのPWAでは運営を脅威モデルに入れられない**こと——
運営はアプリ本体を配信しているので、封筒を復号するまでもなく localStorage の平文キーを
直接読むコードを配れる。

**第3版（本書）**の方針: 運営を脅威モデルから外す。そのうえで、
**復号の鍵素材をサーバーへ一度も送らない**（vault key）ことで、
サーバーが受動的に持ってしまう情報からは復号できないようにする。

### 2.2 守れる相手

| 相手 | 根拠 |
|---|---|
| D1の保存データを見た者（DBダンプ、バックアップ、エクスポート、SQLコンソール、D1の漏えい） | 保存されるのは封筒（暗号文）だけで、鍵素材はどこにも無い |
| **リクエストログ・WAF・トレース・中間層を見た者** | vault key はリクエストに一度も現れない。ここが第2版からの実質的な前進 |
| 通信経路上の中間者 | TLSに加えた二重化 |
| 別の部屋の資格情報を持つ者 | AADに部屋IDを縛るため、封筒を自室へ移植しても開かない |
| room secret（`wk_`）だけを持つ者 | 封筒の鍵は vault key から派生する。secret からは導けない |

### 2.3 守れない相手（正直に書き、UIにもそう表示する）

| 相手 | 理由 |
|---|---|
| **アプリを配信する運営** | 同一オリジンのPWAなので、ブラウザ内の平文キーを読むコードを配れる。暗号では解けない |
| 端末の localStorage / sessionStorage を読める者 | すでに平文のAPIキーがそこにある |
| 引き継ぎコード全体を持つ者 | それは本人。持ち回れることが機能の目的 |
| 端末上で動く悪意あるスクリプト | CSP・SRIの担当領域 |

### 2.4 UI文言（この脅威モデルの帰結）

「運営は読めません」と書いてはいけない。「サーバーは読めません」も、運営＝サーバーの
配信元なので誤解を招く。書いてよいのは:

> APIキーは暗号化してから同期します。復号に必要な鍵は引き継ぎコードの中だけにあり、
> WordBankのサーバーへは一度も送られません。データベースにも通信ログにも残らないため、
> 保存されたデータからは読み取れません。
> ただしWordBank自体はこのアプリを配信しているため、その気になれば読み取れます。
> 誰にも預けたくないキーは、この機能をオフのままにしてください。

## 3. 封筒の置き場所

同期stateの**トップレベル**に `aiSecrets` を置く。`words` / `decks` と兄弟。

**`appState` には入れない**。理由:

- `normalizeState()` はホワイトリストで出力を組み立てるため、受信したstateの `aiSecrets` は
  `appState` に入らない。結果として:
  - ローカルの保存形式（`localStorage` のアプリ状態）が変わらない
  - JSONバックアップ・エクスポート・Undo退避に封筒が混入しない
  - `mergeAppStates()` などのマージ経路に一切触らない＝学習履歴の統合ロジックが無傷
- 封筒は**キャッシュであって正本ではない**。正本は常に各端末のローカルキー。

実測で確認済み: `normalizeState()` を実コードから取り出して `aiSecrets` を含むstateを
通したところ、出力キーは
`activeDeckId, decks, deletions, learningSchemaVersion, quizCounter, savedAt, streak, trash, words`
のみで、封筒の痕跡はJSON全体のどこにも残らなかった（凍結ゲート G8）。

サーバーは state を不透明に扱う（`words` / `decks` が配列であることと全体サイズしか見ない）。
**サーバー変更もマイグレーションも不要**。

## 4. 封筒フォーマット

```json
{
  "v": 1,
  "alg": "A256GCM",
  "kdf": "HKDF-SHA-256",
  "iv": "<base64: 12バイト>",
  "ct": "<base64: 暗号文＋128bitGCMタグ>",
  "updatedAt": 1753500000000
}
```

平文（`ct` の中身、JSON）:

```json
{
  "v": 1,
  "keys": {
    "gemini": { "value": "…", "updatedAt": 1753500000000 },
    "groq":   { "value": "…", "updatedAt": 1753400000000 }
  }
}
```

- **provider ごとに `updatedAt` を持つ**。初版は Gemini / Groq をひとつの全量
  スナップショットとして扱っていたが、それだと「端末AがGeminiだけ更新、端末Bが
  Groqだけ更新」で後からPUTした側が相手の更新を巻き戻す。provider単位の時刻に
  すると、採用も provider 単位になり、この巻き戻りが起きない。
- 外側の `updatedAt` は provider 時刻の**最大値**。復号前に読める粗いふるいとして使う。
  復号後に「最大値と一致するか」を検証し、一致しない封筒は破棄する
  （外側だけを新しく見せかける細工の防止）。
- AAD は `wordsnap-ai-secrets|<v>|<alg>|<kdf>|<roomId>`。部屋IDに加えて版とアルゴリズム名を
  縛り、将来2つ目の方式を足したときの algorithm confusion を防ぐ。
- 封筒全体で 8KB 上限。実測では254バイト。超える封筒は作らないし読まない。
- `v` / `alg` / `kdf` は**完全一致以外すべて拒否**（未知の版を推測で開かない）。

## 5. 鍵派生と vault key

封筒の鍵は **room secret からは派生しない**。サーバーへ一度も送られない乱数
（vault key）から派生する。

```
vaultKey = "wv_" + 64hex     // 32バイトのCSPRNG乱数。端末で生成し、サーバーへ送らない
IKM   = UTF-8(vaultKey)
salt  = UTF-8(roomId)
info  = UTF-8("wordsnap-ai-secrets-v1")
key   = HKDF-SHA-256(IKM, salt, info) -> AES-GCM 256bit
```

room secret を使わない理由は2章。secret は `x-room-key` で毎回サーバーへ送られるため、
そこから派生した鍵は、リクエストログを持つ者・過去のリクエストを記録した者に導かれうる。
**認証は `wk_` のまま一切変更しない**（変更しようとして取り下げた記録は
`docs/sync-auth-v3-design.md`）。

- `extractable: false` で派生する。派生鍵はメモリ上のみ。localStorage にも IndexedDB にも
  保存しない（vault key があればいつでも再派生できる）。
- IVは**毎回** `crypto.getRandomValues(new Uint8Array(12))` で新規生成する。
  同じ派生鍵でのIV再利用はGCMを破綻させるため、再暗号化のたびに必ず新しいIVを引く。
- GCMタグは128bit（WebCryptoの既定）。

### 5.1 引き継ぎコードの拡張

```
現在: wr_<32hex>.wk_<60hex>
新:   wr_<32hex>.wk_<60hex>.wv_<64hex>
```

- **2要素の旧コードも受理し続ける**。vault key 無しの資格情報として扱い、
  同期は今までどおり動く。使えないのはAIキーの暗号化同期だけ。
- 解析は3要素目を任意にする。既にパスワードマネージャへ保存されている2要素のコードが
  無効になることは無い。
- vault key は**同期stateへは絶対に入れない**。入れた瞬間にサーバーへ送られ、
  この設計の意味が消える。運ぶ経路は引き継ぎコードだけ。

### 5.2 vault key のライフサイクル

| 状況 | 動作 |
|---|---|
| 新しい部屋を作る（手動create / 新規ユーザーへのネイティブ自動発行） | secret と同時に vault key も生成。引き継ぎコードは最初から3要素 |
| 既存の部屋で初めてトグルをONにする | vault key を生成して保存し、**新しい引き継ぎコードの保存を促す**。古いコードのままでは他端末が復号できない |
| 3要素コードで合流する | vault key ごと受け取る。すぐ使える |
| 2要素コードで合流する | vault key 無し。トグルをONにすると新規生成になるため、下の分岐に注意 |

**分岐のリスク**: 2つの端末がそれぞれ独立に vault key を生成すると、互いの封筒を
復号できなくなる。vault key はサーバーへ送れない（送ったら意味が無い）ので、
サーバー経由で合意させることはできない。したがって:

- vault key の生成は**ユーザーの明示操作**（トグルをONにする）でのみ行う。
  起動時や同期中に勝手に作らない
- 生成時に「他の端末では新しい引き継ぎコードが必要になります」と必ず表示する
- 分岐しても**データは失われない**。復号できない封筒は黙って無視され、各端末は手元の
  キーを使い続ける（フェイルセーフ）。困るのは同期が効かないことだけで、
  新しいコードを配り直せば直る

## 6. 送信規則

`buildSyncPayloadState()` が唯一の付与点。以下を**すべて**満たすときだけ `aiSecrets` を付ける:

1. 同期トグル `wordsnap-ai-key-sync` が `"1"`
2. **現在の送信経路がV2である**（`syncRequestRoute().isV2` かつ その `roomId` が
   active な資格情報の `roomId` と一致する）
3. **その資格情報が vault key を持っている**（2要素の旧コードで合流した端末は持たない）
4. その roomId 向けの封筒が、最新世代として生成済みである

条件2は現状「active な V2 資格情報が存在する」と等価である（`syncRequestRoute()` は
active な V2 資格情報があれば legacy の同期IDが併存していても必ず V2 経路を返す）。
それでも**経路で書く**。等価でなくなった瞬間に、暗号化された封筒が legacy の部屋
（同期キーを知る者なら誰でも読める）へ静かに置かれるようになるため。

`buildSyncPayloadState()` の呼び出し元は3か所で、うち2か所（手動createと新規ユーザーへの
ネイティブ自動発行）は資格情報がまだ `pending` の状態で呼ばれる——`activateV2Credential()`
は応答を受けた**後**に走るため、その時点では条件2が偽になり封筒は付かない。これは望ましい
（新品の部屋に封筒を急ぐ必要はなく、次の通常pushで乗る）。封筒が実際に乗るのは
`syncPutState()` の通常push経路だけ。

### 6.1 非同期生成と世代管理

封筒の生成は非同期（`crypto.subtle`）だが、`buildSyncPayloadState()` は同期関数として
多数の場所から呼ばれている。**シグネチャは変えない**。キーが変わったタイミングで封筒を
非同期に作り直してメモリに保持し、`buildSyncPayloadState()` はできあがっている封筒を
読むだけにする。

ここで**完了順の逆転**が起きうる。キーをK1→K2と続けて変更したとき、K1の暗号化が後から
完了するとK1が最新キャッシュになってしまう。暗号化中に部屋が切り替わった場合も同様。
そこで:

- 生成のたびに単調増加する世代番号を割り当てる
- 完了時、**自分の世代が今も最新であり、かつ roomId が今の部屋と一致する**ときだけ
  キャッシュへ公開する。そうでなければ結果を捨てる
- キャッシュには roomId を必ず添える。`buildSyncPayloadState()` は roomId 不一致の
  キャッシュを使わない

### 6.2 キー変更だけでは送信が起きない問題

APIキーを入力・削除しても、単語や学習状態を変更しなければ現在の `setAiKey()` 経路は
同期送信を予約しない。封筒だけ作っても永久に送られないため、**最新世代の封筒生成が
成功した時点で送信を予約する**。トグルOFFのときは予約しない（既存ユーザーに余計な
通信を発生させないため）。

## 7. 受信規則

`syncRequest()` の共通境界で `data.state?.aiSecrets` を採用する。

**採用処理は `syncRequest()` の return より前に await する。** 初版は
fire-and-forget にしていたが、それだと「新しい封筒を受信 → 学習stateをマージ →
即座に再PUT」の流れで、まだ採用が終わっていない古いキャッシュが送信され、
受信したばかりの新しいキーを巻き戻せる。採用の失敗は内部で握り潰すので、
await しても同期経路が止まることはない。

採用を**中止**する条件（いずれも黙って無視し、ローカルのキーをそのまま使う）:

| 条件 | 理由 |
|---|---|
| トグルOFF | 明示的な意思表示 |
| V2 active でない／経路がV2でない | 経路が違う |
| **vault key を持っていない** | 鍵素材がない（2要素の旧コードで合流した端末） |
| 応答の `verifiedSyncTarget` が現在の roomId と違う | 通信中に部屋が切り替わった |
| **`revision` 指定のGET（履歴の版）** | 7.1 |
| 封筒が無い / 形が違う / 8KB超 / `v`･`alg`･`kdf` 不一致 | 異常データ |
| 外の `updatedAt` が provider 時刻の最大値と一致しない | 外側だけの細工 |
| 外の `updatedAt` が**現在時刻より24時間以上未来** | 時計ずれ・細工による恒久的な優越の防止 |
| provider の時刻がその provider のスタンプ**以下** | 巻き戻り防止（provider単位） |
| 復号失敗（GCMタグ不一致・AAD不一致・鍵不一致） | 改竄または別部屋の封筒 |
| `keys` の形式不正 | 異常データ |

採用時は **`setAiKey()` を経由する**。受信端末の「この端末に保存」設定が尊重され
（OFFの端末では sessionStorage 止まり）、Geminiのキー変更時にモデル記憶を破棄する
既存の不変条件も保たれる。

空文字のキーは「削除」として採用する。provider単位の時刻で勝敗が決まるため、
古い端末や古いタブが後から削除を復活させることはない。

**ログには封筒の中身も長さも出さない。**失敗は黙って無視する。

### 7.1 `revision` 指定のGETでは採用しない

履歴からの版の復元（`syncRequest("GET", null, { revision })`）は古い版のstateを返すため、
**古い封筒**が含まれる。スタンプが正常なら弾かれるが、スタンプを失った端末や新しい端末では
採用されてしまう。単語を過去の版へ戻すことと、APIキーを過去へ戻すことは別の意思決定なので、
この経路では封筒を一切見ない。

### 7.2 トグルをONにした直後の完全GET（これが無いと機能が黙って何もしない）

**初版の致命的な見落とし**。新しい端末が引き継ぎコードで合流すると
`activateV2Credential()` が現在の `stateRev` を記録する。その後の定期GETは `sinceRev` 付きで
送られ、サーバーは部屋のstateが変わっていない限り `state: null, notModified: true` を返す。
つまり **`aiSecrets` は応答に含まれず、ユーザーがトグルをONにしても何も起きない**——
誰かが単語を編集して revision が上がるまで、キーは永久に届かない。

そこで、**トグルをONにした時点で `sinceRev` を付けない完全GETを1回行い、その応答から
採用する**。合流直後・JSONからの資格情報接続直後にトグルをONにした場合も、この経路で拾える。

### 7.3 409（競合）応答の封筒

409の応答本文には相手の最新stateが入っており、呼び出し側はそれをマージして再PUTする。
ここで封筒を無視すると、自分の古いキーで相手の新しいキーを上書きしうる。
そのため**409応答の封筒も採用対象にする**。
（採用しなくても、相手の端末が次のGETでこちらの古い封筒を時刻で拒否し、自分のキーを
再送するので最終的には収束するが、往復が1回増えるうえ利用者から見て不可解な挙動になる。）

### 7.4 `syncRequest()` を通らない受信経路（意図的にフックしない）

| 経路 | 採用しない理由 |
|---|---|
| 引き継ぎコードの取り込み | アプリ中で最も繊細なマージ（`mergeAppStates` → `activateV2Credential`）を含み、触る危険が見合わない。トグルは合流後にしか出せないので、7.2の完全GETで拾える |
| legacy部屋の取り込み（ネイティブ切替） | 相手はlegacyの部屋であり、6章の送信規則によりそこに封筒は存在しない |

## 8. 単調性スタンプ

`wordsnap-ai-secrets-at`（localStorage、秘密ではない）に **provider ごとの時刻**を
JSONで持つ: `{"gemini":1753500000000,"groq":1753400000000}`。

意味は「この端末が今持っている、その provider のキーの時刻」。

| 出来事 | スタンプ |
|---|---|
| ローカルでキーを変更した（`setAiKey` で値が実際に変わった） | その provider を `Date.now()` に |
| 封筒からその provider を採用した | その provider を封筒の値に |
| 封筒を作る | 各 provider のスタンプをそのまま入れる |

採用条件は provider ごとに `envelope.keys[id].updatedAt > stamp[id]` のみ。
プロトタイプで以下を実測した:

- 古い版の復元で届いた古い封筒を採用しない
- 手元で今書き換えたキーが、それより古い封筒に潰されない
- 2端末が同時に編集しても、より後に編集した側へ収束する
- 削除（空文字）も正しく伝搬する

**スタンプの永続化は必須**。メモリだけに持つと、再読み込みでスタンプが0に戻り、
古い封筒を採用してしまうことを実測で確認した。

**時計ずれ**: 未来にずれた端末が封筒を作ると、正常な端末の更新が恒久的に「古い」と
判定されうる。緩和として、(a) 受信時に現在時刻より24時間以上未来の封筒を拒否し、
(b) 送信時のスタンプは `max(Date.now(), 既存スタンプ + 1)` とする。完全な解決には
サーバー側の論理カウンタが要るが、この規模では過剰と判断した。

## 9. 設定UI

`renderAiKeyFields()` に「APIキーも同期する」トグルを追加する。

- **既定OFF**。`wordsnap-ai-key-sync` が未設定なら OFF。
- **V2 active のときだけ表示**する。legacy運用中はトグル自体を出さない。
- ONにした瞬間に 2.3 の文言を出し、**運営は技術的に読み取れる**ことを明示する。
- ONにした直後に 7.2 の完全GETを1回行う。

**既存の説明文の修正が必須**。現在の

> キーはこの端末のブラウザだけに保存され、WordBankのサーバーへは送信されません。

はトグルONのとき**虚偽になる**。ON時は 2.3 の文言に切り替える。

## 10. 既知の制約（この設計では解かないこと）

正直に書き残す。将来これらが問題になったら、その時点で作り直す。

1. **アプリを配信する運営はキーを読み取れる**（2章）。同一オリジンのPWAである限り、
   暗号では解けない。解くには運営とは独立に配布・検証できるクライアントが要る。
2. **複数タブでキーが食い違いうる**。APIキーは既定でタブ固有の sessionStorage にあり、
   タブ間で共有されない。BroadcastChannel による同期は入れない。
3. **悪意あるサーバーによる完全リプレイ**は、既知スタンプを持たない新端末では検出できない。
   サーバー外の単調性の根拠が無いため。
4. **provider をまたぐ原子性は無い**。Gemini と Groq は独立に勝敗が決まる。

| 古いクライアント | `aiSecrets` を知らないので無視する。壊れない |

## 12. 切り戻し

1. **利用者側**: トグルをOFFにする。以後この端末は封筒を作らず読まない。
   次のPUTで部屋からも封筒が消える。ローカルのキーは残る。
2. **開発側**: `AI_KEY_SYNC_AVAILABLE` を `false` にして再デプロイする。手順の詳細は
   **§16.2 が唯一の正**なのでそちらに従う。データ移行は発生しない。
   部屋に残った封筒は、誰も読まない未知キーとして次のPUTで自然に消える。

> ⚠️ **コミットの `revert` はしてはならない。** 引き継ぎコードの3要素解析まで戻ると、
> 配布済みの新しいコードが解析できなくなり、利用者を締め出す。
> （この節はかつて「revert するだけ」と書いており、§16.2 と矛盾していた。
> 事故対応中に読む文書で手順が2つあるのは危険なので、§16.2 へ一本化した。）

## 15. 実ブラウザ検証で見つかった欠陥（凍結ゲートでは出なかったもの）

本番APIへ中継するローカルプロキシを別ポートで2つ立て、別origin＝別端末として検証した。
実行可能なゲートを338件通した後でも、以下の2件は実ブラウザでしか出なかった。

1. **新規ユーザーはリロードするまでトグルが出ない**。V2資格情報の自動発行は非同期で、
   設定画面の初回描画のほうが先に走るため、描画時点では `getActiveV2Credential()` が
   null だった。→ `renderV2CredentialUi()` と `applySyncIdentityUi()` から表示の要否を
   ときどき見直す（要否が変わったときだけ描き直し、入力中の欄を壊さない）。
2. **「この端末に保存」オフだと、開き直すたびに貼り直しになる**。既定がオフなので
   これは例外ではなく**最も普通の使われ方**。タブを閉じるとキーは消えるが、スタンプは
   localStorage に残るため、封筒の時刻とスタンプが等しくなり `>` の判定で復元されなかった。
   → 時刻が等しく、手元が空で、封筒に値があるときだけ復元する。巻き戻りにはならず
   （そのスタンプが表す状態へ戻すだけ）、削除の伝搬も壊れない（空を空で上書きしない）。

検証した経路: 新規ユーザーのV2ネイティブ発行＋vault key生成 / トグルの表示と文言の切替 /
有効化 → 封筒の送信 → **本番サーバー上に平文キーもvault keyも存在しないことの確認** /
持続オフでの復元 / 引き継ぎコードでの別端末合流 → 有効化 → **キーの受け取り**
（スタンプが送信側と完全一致することで封筒由来だと確認）/ legacy端末でトグルが出ないこと /
pending資格情報では有効にならないこと。

検証で作った本番データ（3部屋・5状態）は削除し、rooms=15 / states=96 のベースラインへ戻した。

## 16. デプロイの安全性（判断の根拠）

### 16.1 トグルOFFの利用者に起きること（全経路の洗い出し）

既存ユーザー2名は両方ともOFFのままデプロイを迎える。触った経路は次のとおり。

| 経路 | OFFのときの挙動 |
|---|---|
| `syncRequest()` | `adoptAiSecretsFromState()` を1回awaitする。`aiSecretSyncRoute()` が即nullを返すため、通信もストレージ書き込みも起きない。関数全体がtry/catchで、例外は外へ出ない。GETごとにマイクロタスクが1つ増えるだけ |
| `buildSyncPayloadState()` | 封筒がnullなのでプロパティを作らない。**送信本文はJSON文字列レベルで従来と完全一致**（ゲートで固定） |
| `setAiKey()` | APIキーを変更したときだけ `wordsnap-ai-secrets-at`（provider別の時刻。秘密ではない）を書く。送信予約は `aiKeySyncEnabled()` が偽なので起きない |
| `normalizeV2Credential()` | vault keyを持たない既存の資格情報にはフィールドを足さない。**保存内容が1バイトも変わらない**（ゲートで固定） |
| `parseV2TransferCode()` | 2要素の旧コードを従来どおり解析する |
| `renderAiKeyFields()` | トグルを描画しない。説明文も従来のまま |
| telemetryのredaction | 伏せる対象が1つ増えるだけ |

**OFFの利用者に観測できる変化は、APIキーを変更したときに localStorage のキーが
1つ増えることだけ。**同期の内容・回数・タイミングは変わらず、単語も学習履歴も
JSONバックアップも一切影響を受けない。

このスタンプの書き込みをOFFのときだけ止めることも考えたが、止めない。
スタンプは「この端末のキーが最後に変わった時刻」という不変条件そのもので、
OFFの間だけ記録しないと、後で有効化したときに古い時刻の封筒を作ってしまう
（他端末が正しく拒否し、結果として同期が効かない）。

### 16.2 切り戻し

**`AI_KEY_SYNC_AVAILABLE` を `false` にして再デプロイする。** これだけ。

- 封筒の作成・送信・採用と、設定トグルの表示がすべて止まる
- **引き継ぎコードの3要素解析は残る**ので、配布済みの新しいコードで合流できる
- 部屋に残った封筒は、誰かの次のPUTで自然に消える
- 各端末のローカルのAPIキーは無傷

コミットの `revert` はしないこと。解析まで戻ると、配布済みの3要素コードが
解析できなくなり、利用者を締め出す。

実際に `false` にして検証済み: 機能経路のゲートだけが落ち、既存ユーザー保護の29件と
引き継ぎコード解析の32件は通り続ける。

### 16.3 デプロイ直後に確認すること

1. `https://wordbank.pages.dev` が200で開く（エッジ伝播の遅延があるので数回試す）
2. 既存V2端末で単語が消えていない。同期バッジが live になる
3. legacy端末でトグルが出ない。説明文が従来のまま
4. D1の `rooms` / `states` の件数が変わっていない

### 16.4 差分レビュー（Codex）で止められた2件

デプロイ直前の差分レビューで、実行可能ゲート344件を通した後に2件が見つかった。
どちらも実在し、修正してからデプロイした。

1. **ON端末を再読み込みすると、部屋から封筒が消える**（高確率）。
   封筒のキャッシュはメモリ上にしかないので再読み込みで空になる。起動時のGETで
   届いた封筒が手元と同じ内容だと `changed = false` で早期returnし、キャッシュが
   空のまま残る。その状態で単語を1つ編集すると、次のPUTから `aiSecrets` が落ちて
   部屋から封筒が消え、他の端末の同期が止まる。
   → 採用の有無にかかわらず、経路が有効ならキャッシュを必ず用意する（`finally`）。
   トグルOFF・legacy・vault key無しは `finally` に入る前に返すので影響しない。

2. **復号を待っている間に別の部屋へ合流すると、旧部屋のキーが新しい部屋へ混ざる**。
   `openAiSecrets()` は非同期で、その前後で `aiSecretSyncRoute()` を取り直していなかった。
   → 復号後・キー適用前に部屋IDと vault key の両方を再確認する。
   `refreshAiSecretEnvelope()` とキャッシュ照合も vault key を見るようにした
   （同じ部屋IDのまま3要素目だけ差し替わる経路がある）。

あわせて、JSON書き出しに vault key を含めるようにした。含めないと、そのJSONから
復元した端末はAIキー同期を復旧できず、再度有効にすると別の vault key を作って
他端末と分岐する。`secret`（部屋への全権限）を既に含めている同じ明示同意の下なので、
リスクの区分は変わらない。
