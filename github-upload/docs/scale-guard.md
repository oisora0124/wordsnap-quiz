# 語数が増えたときの計算量を固定する（2026-08-07）

## なぜ要るか

内蔵の単語帳だけで6種×1500語ある。全部入れれば9000語で、
自分で取り込む人はさらに増える。

ここで O(n²) を踏むと、**語数が2倍になるたびに待ち時間が4倍**になり、
ある日を境に使えなくなる。しかも症状は「同期のたびに固まる」であって、
機能そのものは正しく動くので、既存のテストにも目視にも一切かからない。

同期のたびに全語を通る処理が3つある。

| 処理 | いつ走るか |
| --- | --- |
| `normalizeState` | 読み込み・同期のたび（両側） |
| `mergeAppStates` | 同期のたび。両側の全語を突き合わせる |
| `stateSignature` | 差分判定のたび |

## いまの実測値

このマシン（Apple Silicon）で、履歴8件つきの単語を使った測定。

| 語数 | `mergeAppStates` | 1語あたり |
| --- | --- | --- |
| 2,000 | 89 ms | 44.5 µs |
| 4,000 | 164 ms | 40.9 µs |
| 8,000 | 311 ms | 38.8 µs |
| 16,000 | 629 ms | 39.3 µs |

**1語あたりが一定＝線形。** 二次の兆候はない。

ただし絶対値は軽くない。9000語で約350ms、スマホは3〜5倍遅いので
**1〜2秒のあいだ画面が固まる**計算になる。これは計算量の問題ではなく
定数の問題なので、直すなら分割実行やWorkerへの移動といった
**挙動が変わる改修**になる。仕様を変えない方針のため、いまは手を付けていない。
記録として残しておく。

## 検査の方法（比ではなく「1語あたり」を見る）

最初は「Nを2倍にしたとき何倍になるか」で見ていた。**これは失敗した。**

わざと二次のループを注入して確かめたところ、2000→4000語の比は
2.39 にしかならず、「線形なら約2倍」という判定をすり抜けた。
係数の小さい二次項は、その規模ではまだ線形コストに埋もれている。

**1語あたりの時間**で見ると、線形なら一定・二次なら規模に比例して増えるので、
はっきり分かれる。

| | 2,000語 | 16,000語 | 比 |
| --- | --- | --- | --- |
| いまの実装 | 52.4 µs/語 | 50.9 µs/語 | **0.97** |
| 二次を注入 | 68.2 µs/語 | 163.6 µs/語 | **2.40** |

閾値は 1.5。実測の余裕は `normalizeState` 0.99、`stateSignature` 0.99、
`mergeAppStates` 0.97 で、どれも十分に離れている。

測定はサイズごとに複数回まわして**最小値**を採る。
CPU負荷のばらつきは常に遅い方向にしか出ないので、最小値がいちばん安定する。
5回連続で通ることを確認済み。

## 合成データが本番の形と違うと、測っているつもりで何も測っていない

ここで2つ踏んだ。どちらも **Codex の独立レビューが見つけた**もので、
テストは全部緑のまま通っていた。

| 誤り | 何が起きていたか |
| --- | --- |
| 単語帳を `deck` という名前で入れていた | 本番が読むのは `deckId`。単語帳の突き合わせが1度も走っていなかった |
| `decks: []` にしていた | 単語帳リストの走査（`decks.find`）が空振り |
| seed の差を `updatedAt` に付けていた | `normalizeWord` が保持しないフィールドなので、正規化後の local と remote がほぼ同一になり、マージがほとんど仕事をしていなかった |
| 削除記録・ゴミ箱を空にしていた | どちらも正規化と突き合わせの対象なのに未測定 |
| 削除記録・ゴミ箱の時刻を固定の過去日時にした | TTL（90日 / 30日）で全部捨てられ、「入れたつもりで空」になっていた |

いまは `deckId` + 6件の単語帳、正規化を通っても残るフィールドでの差分、
語数に比例した削除記録とゴミ箱を入れている。
マージの検査でも「local と remote の署名が違うこと」を先に確かめ、
両者が同一のままマージが素通りする状態を弾いている。

## 検査が空振りしていないことの確認

`mergeAppStates` と `normalizeState` にそれぞれ二次のループを注入し、
どちらもこのゲートが落ちることを確認した（2.40倍・4.70倍）。5回連続で通ることも確認済み。

比だけを見ていると、線形のまま定数倍が10倍悪化しても通ってしまうので、
9000語（内蔵を全部入れた規模）の同期1回ぶんに緩い絶対上限（5秒）も置いてある。

速度だけを見て中身を見落とさないよう、同じファイルで
「2000語のマージ後に語数・ID重複・履歴・学習状態が保たれている」ことも見ている。

## 見ていないこと

- 描画（DOM）の計算量。ここは node では測れない。
  9000語での一覧のフィルタ・ソートは全単語を走査するが、未測定。
- 取り込み・OCR・クイズ生成の計算量。
- 実機（スマホ）での絶対時間。上の換算は倍率からの推定でしかない。
- **単語帳の数**に対する計算量。いまは6件で固定して測っている。
- **履歴の長さ**に対する計算量。いまは8〜12件で固定している（本番は最大50件）。
- 実ブラウザでの復旧・import/undo の一連の流れ（LocalStorage・複数タブ・SW との組み合わせ）。
- メモリ使用量。

## 実行

`npm test` に同梱（5件、約6秒）。単体は `npm run test:scale`。
