# サーバー側データの保持方針（2026-08-07）

## 大原則: 進捗は「休眠」を理由に消さない

D1 の `states` には `appState` が丸ごと入っている。単語・履歴・学習状態・単語帳・
ゴミ箱のすべてで、**これが利用者の進捗の唯一の控え**である。

「長期間アクセスが無い行を消す」は、一見すると容量対策として妥当に見える。
**やってはいけない。**

端末の localStorage には残っているので、その端末を使い続ける限り誰も気づかない。
壊れるのは**再開しようとした瞬間**だけである。

- 半年ぶりに開いたら機種変更していた
- サイトデータを消してしまった
- 新しい端末で引き継ぎコードを入れた

このとき控えが消えていれば進捗は失われる。しかも「久しぶりに再開する人」は、
まさに休眠判定に引っかかる人であり、**消す対象と、助けが要る人が完全に一致する**。

アプリの説明文も「長期間まったくアクセスされないサーバー保存分を定期削除する機能は、
現在はありません」と利用者に伝えている。これは欠落ではなく設計である。

## テーブルごとの方針

| テーブル | 中身 | 保持 | 根拠 |
| --- | --- | --- | --- |
| `states` | `appState` 丸ごと＝**進捗の控え** | **無期限** | 消すと復元経路が消える（上記） |
| `rooms` | V2の `roomId → stateKey` | **無期限** | 消すと引き継ぎコードが使えなくなる |
| `feedback` | 利用者が書いた要望 | **無期限** | 読む前に消える事故を避ける。閲覧はダッシュボードSQLのみ |
| `state_revisions` | 過去状態の履歴 | 上位5件＋直近7日の日次 | PUTのたびに適用 |
| `rate_limits` | レート制限のカウンタ | 窓が明けたら削除 | 4経路すべてが毎回掃除 |
| `telemetry` | 匿名の利用回数とエラー | **180日** | 集計値のみ。進捗と無関係 |

## `telemetry` の保持期限（1.0.73 で追加）

### なぜ入れたか

追記しかしないテーブルで、掃除が無かった。上限は 1IPあたり 60req × 20件/日。

| 利用者 | 最悪の増加量 | 5GB（D1無料枠）に届くまで |
| --- | --- | --- |
| 2名 | 2,400 行/日 | 数十年 |
| 50名 | 60,000 行/日 | 約2.3年 |
| 1,000名 | 1,200,000 行/日 | 約6週間 |

実際はクライアントが localStorage で名前ごとに集約してから送るので、
これよりずっと少ない。それでも利用者が増えれば線形に効いてくる。

### どう動くか

- `pruneOldTelemetry(db, now)` が、**1回あたり最大500行**の上限付きで削除する。

  ```sql
  DELETE FROM telemetry WHERE id IN (
    SELECT id FROM telemetry WHERE created_at <= ? ORDER BY created_at LIMIT 500
  )
  ```

  上限を付けない `DELETE ... WHERE created_at <= ?` にしてはいけない。
  D1 は1クエリ30秒の上限があり、溜まった行が多いと届きうる。さらに
  **D1 はDB単位で逐次処理する**ので、長い DELETE の間は通常の INSERT も待たされる。
  期限切れは日々わずかしか増えないので500で足り、溜まっていても窓が明けるたびに減っていく。
- 呼ぶのは**レート制限の窓が明けたときだけ**＝1IPにつき高々1日1回。
  既存の `rate_limits` 掃除と同じ場所に相乗りしており、書き込み回数は増えない。
- 自前の `try/catch` で閉じてあり、掃除の失敗が統計の保存や応答に響かない。
- `migrations/0007_telemetry_created_at.sql` で `created_at` に索引を張った。
  索引が無いと全表走査になり、**行が増えるほど遅くなる**＝
  掃除が必要になる場面でこそ重くなる。

### デプロイの順序（重要）

**Pages のデプロイと D1 マイグレーションの適用は別の操作**である。
`0007_telemetry_created_at.sql` は push しても自動では適用されない。

```bash
npx wrangler d1 execute <DB名> --remote --file migrations/0007_telemetry_created_at.sql
```

適用しなくても掃除は動く（索引が無いぶん遅くなるだけ）ので、順序はどちらでもよい。
ただし**索引が無いまま行が増えると全表走査が重くなる**ので、早めに当てる。

### 投入時の影響

**デプロイ直後は1行も消えない。** 匿名統計の運用開始は 1.0.22（2026-07-25）で、
180日を過ぎる行が出るのは **2027-01-21** 以降。そこから毎日、
その日に期限を迎えたぶんだけが少しずつ落ちる。一度に大量削除は起きない。

### 180日という値

障害の傾向を追うには十分な長さを取った。これより短くしても得られる容量はわずかで、
失う情報のほうが大きい。検査で 90〜730日の範囲に収まることを固定してある。

## 検査

`scripts/telemetry-contract.test.mjs`（`npm run test:api` / `npm test`）。

- 窓が明けたときだけ掃除が走る（同じ窓の中では走らない）
- cutoff が保持期限と一致し、期限内の行を消さない
- 掃除が失敗しても統計の保存と応答は落ちない
- **対象が `telemetry` だけ**であること
  （FakeD1 が想定外の DELETE を記録し、ソースにも `states` / `rooms` /
  `feedback` / `state_revisions` への DELETE が無いことを確認）

- 1回の削除に上限が効いていること（上限の3倍の行を仕込み、1回で上限ぶんだけ消えること、
  かつ次の窓でさらに減ること＝詰まらないこと）

変異テストで10通りの壊し方を試した。9件は検出。すり抜けた1件は
`pruneOldTelemetry` の内側の `try/catch` を外すもので、呼び出し元も外側で
`catch` しているため観測できないと判明した。冗長だが、呼び出し元が変わっても
「掃除は何も壊さない」が局所で保証されるように残してある（コードにも明記）。

### FakeD1 に DELETE を実装した理由

実装しないと、未対応SQLとして投げられた例外を `pruneOldTelemetry` の
`try/catch` が握り潰し、**掃除が動いているかを一切検査できない**状態になる。
このリポジトリで過去に繰り返した「スタブが実装の防御を素通りさせる」型の穴なので、
FakeD1 側で実際に行を消して再現している。

## 今後の検討

- 窓が明けた瞬間に同時リクエストが来ると、同じ掃除を複数回投げる。
  上限付きなので1回あたりは軽く、実害は無いと判断した。
  気になるなら、掃除済みを示す印を `rate_limits` に置く手はあるが、書き込みが増える。
- 実D1での `EXPLAIN QUERY PLAN` による索引利用の確認は行っていない（FakeD1では再現できない）。
- `feedback` の保持期限は**入れない**。読む前に消える事故のほうが重い。
  容量が問題になるなら、先に読み終えたものを手動で消すほうが安全。
