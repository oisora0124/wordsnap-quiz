## 見送ったもの

### H4. V2認証失敗の上限判定が、D1照会とHMAC検証の後にある

**指摘**: 形式だけ正しいランダムな部屋ID・秘密を大量に送ると、上限に達した後も
毎回 D1 の SELECT と HMAC 検証が実行される。上限がDoS防止として機能していない。

**事実確認**: そのとおり。`handleV2RoomRequest` は
`selectRoomById` → `verifyRoomSecret` → `v2AuthFailure`（ここで初めて上限を消費）
の順で処理する。

**それでも直さない理由**:

検証の前に上限を見て弾く実装にすると、**現在の契約を2点とも壊す**。

1. 30回失敗した後でも、**正しい資格情報なら成功する**
2. 成功経路は失敗用のバケツを**読みすらしない**

これは意図的な設計で、`scripts/sync-auth-v2-contract.test.mjs` の
「V2認証失敗は30回後に429へ切り替わり、認可成功は超過バケツを参照しない」が固定している。

事前判定を入れると、次の人が締め出される。

- 引き継ぎコードを何度も打ち間違えたあと、ようやく正しく入力した人
  （＝端末を失って復旧している最中の人。最も助けが要る場面）
- 攻撃者と同じNAT配下にいる正規利用者（学校・職場・モバイル回線）

守れるコストは「1回のD1読み取り＋鍵リング分のHMAC」で、鍵リングが1本の現在はごく小さい。
**復旧中の利用者を締め出す代償に見合わない。**

**本来の置き場所**: 処理量そのものを抑えるなら、アプリコードではなく
Cloudflare 側のレート制限ルール（WAF / Rate Limiting Rules）で入口を絞るのが正しい。
これはリポジトリではなくアカウント設定なので、導入するかは運用判断。

**再検討の条件**: 実際に認証失敗の大量発生が観測されたとき、または
鍵リングを増やして1回あたりの検証コストが上がったとき。

### M1b. レート制限がIPv6で回避できた（2026-08-06 修正済み）

`CF-Connecting-IP` をそのままレート制限の鍵に使っていた。IPv6は1契約者に
`/64`（アドレス2^64個）が割り当たるのが普通なので、**アドレスを1つずらすだけで
別人として扱われ、上限が素通りしていた**。IPv4では効く対策が、IPv6では効かない。

対象は4箇所:

- `functions/api/telemetry.js` の `consumeTelemetryRateLimit`
- `functions/api/wordsnap-state.js` の `consumeV2RateLimit`
- `functions/api/feedback.js` の `ipBucket` 呼び出し2箇所

**対処**: `rateLimitClientKey()` を各ファイルに置き、IPv6は `/64` へ丸めてから
鍵にする。IPv4はそのまま使う（NAT配下の同居利用者を巻き込む範囲を広げないため）。
`::` の省略記法と `::ffff:` のIPv4射影、ゾーンID（`%eth0`）も正しく扱う。

**なぜ共有モジュールにしないか**: `functions/api/` に共有モジュールを置く構成に
なっておらず、ビルド工程も無い。3ファイルへ同じ実装を置き、
`scripts/rate-limit-key.test.mjs` が**3実装の出力が一致すること**を検査する
（コピーのずれが最大のリスクなので、そこを直接固定した）。

**残る限界**: 攻撃者が複数の `/64` を持つ場合は依然として回避できる。処理量そのものを
抑えるなら、下の M1 と同じく Cloudflare 側の WAF / Rate Limiting Rules が本来の
置き場所になる。これはリポジトリではなくアカウント設定なので運用判断。

### M2. テレメトリのイベント名にサーバー側の許可リストが無い

クライアント側には許可リスト（`USAGE_NAMES`）があり、名前の一致はゲートで固定済み。
サーバー側にも置くと、クライアントに名前を足すたびに両方を直す必要が生じ、
**片方だけ直して黙って捨てられる**という以前と同じ事故（2026-07-26に判明したもの）を招く。

行数の増加は IP 単位の上限と期限切れ行の掃除で抑えているため、当面は見送る。
利用者が増えて実データが溜まってから、保存期限（古い行の削除）を先に入れるほうが効く。

### M7. 結合テストが無い（FakeD1は実D1ではない）→ **2026-08-07 対応済み**

`node:sqlite`（Node標準・依存ゼロ）で migrations を実際に適用し、
本番の Functions をそのまま動かす結合テストを入れた（`scripts/d1-integration.test.mjs`、10件）。
変異テストで、FakeD1 が素通りさせる5種（存在しない列・migration適用漏れ・
列の欠落・ON CONFLICT の対象違い・テーブル定義の狂い）を全部捕まえることを確認済み。
詳細は [d1-integration.md](d1-integration.md)。以下は当時の記録。


指摘は正しい。契約テストのFakeD1は期待するSQLの意味を再実装したもので、
実D1の構文・制約・マイグレーションは通らない。

Miniflare か実D1互換環境の導入は相応の作業量で、いまの利用者2名の規模では
費用対効果が薄い。代わりに、**スタブが実装の防御を素通りさせない**ことを
この回で全ファイル直した（上記の構造的な問題）。

**再検討の条件**: サーバー側のスキーマを変更するとき。そこは FakeD1 では守れない。

## CIについて

`.github/workflows/release-checks.yml` を用意したが、OAuthの `workflow` 権限が無く
push できていない。手順は `README.md` に記載済み。

**ワークフローを置いてもそれだけではデプロイは止まらない。**
Settings → Branches → `main` の必須チェックに `release-checks / test` を
指定して初めて止まる（リポジトリ設定なのでコードに含められない）。
