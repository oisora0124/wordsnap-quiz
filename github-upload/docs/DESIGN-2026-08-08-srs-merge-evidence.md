# 学習状態マージの因果判定（証拠ベクトル）— 設計

対象: `publish/index.html` の `mergeLearningState` / `mergeWord`
記録日: 2026-08-08
関連: `docs/REVIEW-2026-07-27-deferred.md` の D1 / D2

## 1. 直す問題

### D2: 時計が遅れた端末との合流で進捗が巻き戻る

`mergeLearningState` は `srsUpdatedAt`（各端末の `Date.now()`）の大小で勝敗を決める。
既存の `clampSrsTs` は「時計が**進んだ**端末」を弾くが、「時計が**遅れた**端末」は弾けない。
その結果、解答数の少ない端末が新しい時刻を主張して、進んだ端末の学習状態を消す。

実測（本物の解答経路 `applyLearningResult` を通した2端末シミュレーション）:

| | 合流前 | |
|---|---|---|
| 端末A（時計が1時間遅れ・6回正解） | `stage=3 streak=6 mastered` | |
| 端末B（1回だけ正解） | `stage=1 streak=1 review` | |
| **合流後（両端末とも）** | **`stage=1 streak=1 review`** | ← Aの進捗が消える |

被害: 習得済み（次回7日後）だった語が復習（翌日）へ落ちる。過剰出題の方向なので
データは壊れないが、6回分の学習成果が毎回の同期で消え続ける。

### D1: 並行して両端末が正解すると、正答数が1回分消える

`stats.correct` は `Math.max(local, remote, historyCorrect)` で合流する。
両端末が同時期に1回ずつ正解すると `max` は1回分しか拾わない。

ただし `historyCorrect`（合流後の履歴に含まれる正解数）が救うため、
**履歴が50件の上限に達していない語では実害が出ない**。実測:

| 事前の解答回数 | 期待 | 実測 | |
|---|---|---|---|
| 4回（履歴6件） | 6 | 6 | 履歴が救う |
| 60回（履歴50件で頭打ち） | 62 | 61 | **1回分消える** |

被害: 正答率表示と個人適応SRSの単語係数がわずかにずれる。1語につき50回以上
解答した場合に限る。

## 2. なぜ時刻では直せないか（前回の検討で確定した点）

D2 を「正解では段階が下がらない」という不変条件で直そうとすると、
次の2つが**データ上まったく同じ形**（新しい側の段階が低い）で現れる:

- (a) 時計ずれ: 解答数の少ない端末が新しい時刻を主張している（直したい）
- (b) 正当な降格: 誤答で下がったあと正解した状態（`lastSrsResult="correct"` のまま段階が低い）（守りたい）

時刻だけでは区別できない。前回はこれを見落として保護を入れ、(b) を壊すと判明したため取り消した
（`docs/REVIEW-2026-07-27-deferred.md`）。

## 3. 設計: 既にあるデータを因果の時計として使う

### 3.1 中心となる観測

`index.html` の解答処理（`submitAnswer`）は、1問につき必ず次を**同じ経路で**行う:

```js
word.stats[isCorrect ? "correct" : "wrong"] += 1;   // ← 必ず1増える
word.history.push({ at: ..., correct: isCorrect });
applyLearningResult(word, isCorrect, ...);          // ← learning を更新
```

`applyLearningResult` の呼び出しはこの1か所だけで、`learning` を書き換える他の経路は
新規単語の生成（`stats: {correct:0, wrong:0}`）しかない。進捗リセット機能は存在しない。

つまり **`(stats.correct, stats.wrong)` は「この端末がこの語に適用した学習事象の数」** であり、
解答のたびに単調増加する。合流時は成分ごとに `max` を取るので、合流後も単調増加する。
**時計に一切依存しない。**

### 3.2 判定規則

```
証拠ベクトル  ev(word) = (stats.correct, stats.wrong)

支配        ev(X) ≧ ev(Y)  ⟺  X.correct ≧ Y.correct かつ X.wrong ≧ Y.wrong
                             （かつ少なくとも一方が真に大きい）
```

片側が支配していれば、その側は相手の解答を**数の上では**すべて含んでいる。
そちらの学習状態を採用する。支配関係が無い（＝真に並行した更新）ときは、
**既存のロジックをそのまま使う**（時刻LWW → 保守的マージ）。

これで (a) と (b) が分かれる:

| | 端末A | 端末B | 支配 | 結果 |
|---|---|---|---|---|
| (a) 時計ずれ | c=6 w=0 stage3（古い時刻） | c=1 w=0 stage1（新しい時刻） | **A** | Aを採用 → 巻き戻らない |
| (b) 正当な降格 | c=6 w=0 stage3（古い時刻） | c=7 w=1 stage2（誤答→正解） | **B** | Bを採用 → 降格が残る |

(b) では B が誤答1回・正解1回を追加しているので `ev(B) > ev(A)` になり、B が勝つ。
時刻では区別できなかった2つを、事象の数が分ける。

### 3.3 誤答の取りこぼし防止

数だけでは「両端末が別々の誤答を1回ずつ持つ」場合を見分けられない
（`w=1` 同士だが中身が違う）。誤答は「忘れた」証拠で、取りこぼすと
**復習に戻らない＝より害が大きい方向**なので、履歴で照合する:

```
勝った側の履歴が、負けた側の誤答エントリをすべて含むときだけ、証拠による判定を使う。
含まないものがあれば、既存のロジックへ落とす（＝今日と同じ挙動）。
```

**例外は設けない。** 履歴は `WORD_HISTORY_LIMIT`（50件）で切り詰められるので、
「古い誤答は押し出されただけで、勝った側も見ているはず」と免除したくなる。
実際に2通り書いたが、どちらも Codex に破られた（§6.7 の指摘1）:

| 免除条件 | 破られ方 |
| --- | --- |
| 勝った側の最古エントリより古ければ免除 | 履歴の日時は端末の時計由来。時計を先に進めた端末は履歴全体が未来へずれ、相手の正当な誤答を丸ごと「古い」側へ追い出せる |
| 上記に加えて「履歴が上限50件に達していれば」 | ちょうど50問解いただけの端末は一度も切り詰められていない。件数は切り詰めの証明にならない |

**「押し出された」と「見ていない」はデータから区別できない。** 免除をやめれば、
時計を進めた端末が誤答を握りつぶす経路は構成的に存在しなくなる。
代償は、1語に50件以上を積んだ端末で古い共有の誤答が押し出されている場合に
証拠判定が使えなくなること。これは従来判定へ落ちるだけなので安全側で、
押し出された誤答は `dominantLearningEvidence` の誤答数の比較が受け止める。

この設計により「今日より誤答を取りこぼしやすくなる経路は無い」ことが構成的に言える。
証拠で勝敗が変わるのは、勝った側が負けた側の誤答をすべて持っているときだけだから。

### 3.4 検証待ち（仮習得）マークの扱い — **変更しない**

`masteryVerify: "flashcard"` は「期限到来後の4択で確かめるまで本習得にしない」安全装置。

一度、証拠で勝った場合に限り「どちらかが検証待ちなら残す」（OR）に変えた。
消す方の誤りは「未検証のまま習得が確定して出題されなくなる」＝害の重い方向だ、
という理屈だった。**これは誤りで、Codex に指摘されて取り消した**（§6.7 の指摘2）。

合流結果は両端末に保存される。ORにすると、検証を済ませた端末が同期するたびに
相手側の古いマークが復活し、**永久に本習得へ到達できない**。
既存コードが勝った側だけを見ているのはこのループを断つためで、
検証（4択への正解）は必ず正答数を1増やすので、検証した側は
**時刻でも解答数でも勝つ**。勝った側だけを見れば検証結果は正しく伝わる。

### 3.5 変えないもの

- `stats` / `history` の合流規則（`max` と和集合）— **変更なし**
- `srsUpdatedAt` の合流（`max`）と `clampSrsTs`（未来時刻の無効化）— **変更なし**
- 支配関係が無いときの分岐（時刻LWW・保守的マージ）— **変更なし**
- `nextReviewAt` は勝った側の値（`repairFarFutureReviewAt` で400日超は正規化時に0へ）— **変更なし**
- `masteryVerify` の扱い（勝った側だけを見る）— **変更なし**（§3.4）
- `mergeLearningState(a, b)` の2引数呼び出し（既存テスト・リリースゲートが使用）は
  証拠なしとして**従来と完全に同一**の結果を返す

## 4. 安全性の確認

### 4.1 データ構造の変更・移行

**無し。** 新しいフィールドを1つも足さない。`(correct, wrong)` は既存データにそのままある。

- `LEARNING_SCHEMA_VERSION` の引き上げ **不要**
- サーバの `HIGHEST_LEARNING_VERSION` の引き上げ **不要**
- D1マイグレーション **不要**
- 本番の `states` 行（118件）に対する書き換え **不要**

### 4.2 旧版クライアントとの同居

判定はクライアント内のマージ処理だけで完結し、保存形式もAPI契約も変わらない。

- 旧版が新版の書いた状態を読む: フィールドが増えていないのでそのまま読める
- 新版が旧版の書いた状態を読む: 同上
- サーバは学習スキーマ版を見て `409 downgrade_conflict` を返すが、版を上げないので**発火しない**
  （＝利用者に「ページを開き直してください」を出さない。操作は一切要らない）

旧版と新版が混在している間は、旧版側のマージが従来どおり時刻で決めるため
D2 が残る。壊れるのではなく**直っていないだけ**で、両端末が更新されれば直る。
2端末とも次回の読み込みで新版になる。

### 4.3 収束性（振動しないこと）

実装は「A が B を数の上で覆うか」「B が A を覆うか」を独立に求め、
**片方だけが真のときにだけ**勝者を決める。両方真（＝同数）でも両方偽（＝並行）でも
`""` を返して従来判定へ落とすので、**引数の順序に依らない**。
`stats` は `max` で単調増加し、合流後は両端末で一致するため、2往復目には
支配関係が消えて安定する。10往復の収束テストと、可換性のランダムテストで固定する。

### 4.4 想定される劣化と、その向き

| 状況 | 今日 | 変更後 | 向き |
|---|---|---|---|
| 片方が明らかに進んでいる（D2） | 少ない側が勝つことがある | 多い側が勝つ | **改善** |
| 正当な降格 vs 古い高段階 | 降格が残る | 降格が残る（変わらず） | 同じ |
| 真に並行（支配関係なし） | 時刻LWW/保守的 | 同じ | 同じ |
| 支配側が相手の誤答を持たない | 時刻LWW/保守的 | 同じ | 同じ |
| 支配側が相手の正解を持たない | — | 支配側を採用（相手の正解は `stats`・履歴には残る） | 過剰出題側＝安全 |

**データが消える経路は無い。** 単語・成績・履歴・削除墓標の合流は一切触らない。
変わるのは `learning`（段階・連続正解数・状態）をどちらから採るかだけで、
どちらを採っても既存の値の範囲内にとどまる。

### 4.5 前提「解答数は単調増加する」の確認

`stats` を書く箇所は4つしかなく、いずれも減らさない:

| 箇所 | 内容 |
| --- | --- |
| `submitAnswer` | `+= 1`。同じ経路で履歴を push し `applyLearningResult` を呼ぶ |
| `normalizeWord` | `nonNegativeInteger` で丸めるだけ（正常値は変えない） |
| `mergeWord` | `Math.max(local, remote, 履歴の件数)` |
| 単語の新規作成（取り込み・共有単語帳） | `{correct: 0, wrong: 0}`。新しいIDの新しい語 |

サーバ（`functions/api/wordsnap-state.js`）は state を不透明な塊として扱い、
単語の中身を書き換えない（見るのは件数の上限だけ）。

状態を丸ごと差し替える経路（履歴からの復元・強制取得・バックアップ取り込み・全消去）は
`stats` と `learning` を**同じスナップショットから**同時に入れ替えるので、
両者が食い違った状態は生じない。復元後に `stats` が下がることはあるが、
その場合 `learning` も同じだけ古いので、証拠判定はもう一方の端末を勝たせる
＝復元前の進捗が戻る。これは時刻判定でも同じ結論になる（挙動は変わらない）。

### 4.6 既知の限界（許容する範囲）

誤答の照合に例外を設けないため（§3.3）、時計のずれで誤答が握りつぶされる経路は無い。
代わりに、1語に50件以上を積んだ端末では古い共有の誤答が履歴から押し出され、
証拠判定が使えなくなる（＝D2 が直らない語が出る）。従来判定へ落ちるだけなので安全側。

**解答数は「最新の解答」ではなく「取り込んだ解答の数」で勝敗を決める。**
真に並行した更新（互いに相手に無い解答を持つ）で片方が数で勝つ場合、
負けた側の最新の1問（たとえばフラッシュカードの「あやふや」）は学習状態としては
残らない。今日の時刻判定では「最後に答えた側」が勝つので、ここは**判断基準の
入れ替え**であって新しい欠陥ではない。数で勝つ側は相手より多く正解している
（誤答は §3.3 の照合で守られる）ため、この向きを採る。
なお成績と履歴自体は両側とも合流するので、記録が消えることはない。

## 5. この設計で直らないもの

**D1 は直らない。** 「両端末が同じ回数だけ正解した」ことを検出するには、
端末ごとの計数（G-counter）が要る。これは `learning` にフィールドを足す
＝スキーマ版の引き上げ＝旧版の締め出しを伴うため、本設計の範囲外とする。

現状の被害は「1語に50回以上解答した場合に、正答数が並行解答1回分ずれる」に限られ、
学習の進み方（SRSの段階・出題順）には影響しない。`docs/REVIEW-2026-07-27-deferred.md`
に据え置きとして記録する。

## 6. 検証（実施済み）

### 6.1 2端末シミュレーション（本物の `applyLearningResult` 経路）

合成した `learning` ではなく、`submitAnswer` と同じ順序
（`stats` 加算 → 履歴 push → `applyLearningResult`）で状態を進めて合流させた。

| 項目 | 修正前 | 修正後 |
| --- | --- | --- |
| D2（時計1時間遅れ・6回正解 ＋ 1回正解の端末） | `stage=3 mastered` → **`stage=1 review`** | `stage=3 mastered` を維持 |
| 正当な降格（誤答→正解） | 保たれる | 保たれる（変化なし） |
| 10往復の収束 | 1往復目で安定 | 1往復目で安定・両端末一致 |
| D1（事前4回・履歴6件） | 6/6 正しい | 6/6 正しい |
| D1（事前60回・履歴50件上限） | 61/62（1回分消える） | 61/62（**未解決のまま**） |

### 6.2 既存ゲート

`npm test` 600件すべてパス（終了コード0）。追加した11件を含む。とくに次が通っている:

- 「時計が未来にずれた端末の復習予定は取り込み時に0へ戻す」
- 「2端末の往復: 時計の狂った端末の値が、正常な端末の学習を壊さない」
- リリースゲートの `far-future device clock must not override a valid recent learning result`

### 6.3 変異テスト（トートロジー検査）

防御を1つずつ壊し、ゲートが**その理由で**落ちることを確認した。
CSPハッシュ不一致のような無関係な失敗に紛れないよう、変異のたびに `sync:html` を
掛け直し、落ちたテスト名まで照合している。

| 変異 | 検出 |
| --- | --- |
| 証拠判定そのものを外す | ✓ |
| 誤答の取りこぼし照合を外す（常に採用） | ✓ |
| 支配判定の向きを逆にする | ✓ |
| 支配判定から誤答数の成分を落とす | ✓ |
| 証拠を `mergeWord` から渡さない | ✓ |
| 同数のときも支配ありとみなす | ✓ |
| 誤答の照合に「古ければ免除」の窓を戻す（1巡目 指摘1の修正前） | ✓ |
| 検証待ちマークを両側のORにする（2巡目 指摘2＝検証が永久に無効化される） | ✓ |
| 検証待ちマークを勝った側からも採らない | ✓ |

4件目は当初検出できなかった。誤答数の成分が効くのは
「履歴の50件上限から誤答が押し出され、履歴上は全件正解に見えるが `stats` には
誤答が残っている」場合だけで、そのテストが無かったため。テストを足して塞いだ。

なお最初の変異テストは**全件を「検出」と誤判定していた**。変異でHTMLの中身が
変わると先にCSPハッシュ不一致でゲートが落ち、本当の検査へ到達していなかった。
変異のたびに `sync:html` を掛け直し、落ちたテスト名まで照合するようにして
初めて上の4件目の穴が見えた。**落ちたことではなく、落ちた理由を確かめる。**

### 6.4 ランダム試行（自分が思いついた筋書き以外を当たる）

ランダムな2端末の解答列（共通履歴0〜59問、その後それぞれ0〜7問、
時計のずれ±3日）を本物の解答経路で作り、4000通り合流させて検査した。

| 不変条件 | 結果 |
| --- | --- |
| 取り込む向きを変えても学習状態が同じ（可換） | 4000/4000 |
| 2往復目以降で状態が行き来しない（収束） | 4000/4000 |
| 両端末が同じ状態に落ち着く | 4000/4000 |
| 単語・履歴・正答数・誤答数が減らない | 4000/4000 |

この検査自体も一度失敗している。当初は往復合流だけを見ており、
**左右非対称な判定バグを入れても全件パスしてしまった**（履歴の和集合が
成績を押し上げ、同点が自然に崩れて非対称性が隠れる）。単発の合流を
直接比べる可換性の検査を足して、初めて4000件中83件で検出できるようになった。

この可換性検査は `word-merge.test.mjs` に固定種のランダムテスト
（1000通り、うち4割は成績を同点にして分かれ道を狙い撃つ）として常設した。

### 6.5 1.0.74 との総当たり比較（この変更が作れる状態の範囲）

「新しい状態を勝手に作っていないか」を、1.0.74 と 1.0.75 の
`mergeLearningState` に同じ入力を与えて直接比べた。入力は乱数で2万通り
（段階・連続正解数・状態・検証待ち・`lastSrsResult`・時計のずれ±30日・
正答/誤答の履歴をすべてランダム）。

| 確認 | 結果 |
| --- | --- |
| 証拠を渡さない2引数呼び出しが 1.0.74 と完全一致 | 20000/20000 |
| 1.0.74 と結果が変わった件数 | 3140件 |
| そのうち「証拠で勝者が決まっていないのに変わった」 | **0件** |
| そのうち「結果が勝った側の丸写しになっていない」 | **0件** |

**この変更が作りうる状態の集合は、1.0.74 のそれを超えない。**
挙動が変わるのは証拠で勝者が決まったときだけで、そのときの結果は
**勝った側の端末に実在した学習状態をそのまま採ったもの**であり、
合成された新しい状態ではない。

### 6.6 旧版クライアントとの混在

1.0.74 のHTMLと 1.0.75 のHTMLからそれぞれマージ処理を取り出し、
同じアカウントの2端末として交互に同期させた（D2 の状況）。

| 端末の組み合わせ | 収束 | 両端末一致 | 単語・成績・履歴 | 結果 |
| --- | --- | --- | --- | --- |
| 新版 ＋ 新版 | 1往復 | ✓ | 保全 | `stage=5 mastered`（**直っている**） |
| 旧版 ＋ 旧版（比較用の基準） | 1往復 | ✓ | 保全 | `stage=1 review`（巻き戻る＝現状） |
| 新版（進んだ側） ＋ 旧版 | 2往復 | ✓ | 保全 | `stage=1 mastered`（直っていないが壊れない） |
| 旧版（進んだ側） ＋ 新版 | 1往復 | ✓ | 保全 | `stage=1 review`（同上） |

**混在しても押し合いにならず、単語・成績・履歴を1件も失わない。**
旧版が混ざっている間は D2 が残るだけで、両端末が更新されれば直る。

### 6.7 性能

`mergeWord` は同期のたびに全語で呼ばれる（起動時同期の実測は9000語で443ms、
`docs/` の第2層調査）。9000語のマージを7回計測した中央値:

| | 変更前 (1.0.74) | 変更後 (1.0.75) |
| --- | --- | --- |
| 通常の同期（両端末の成績が一致＝支配判定が即座に外れる） | 185ms | 193ms（+4.4%） |
| 全語で支配関係があり、誤答の照合が毎語で最後まで走る最悪ケース | 183ms | 207ms（+13%） |

最初の実装は語ごとに `Set` と中間配列とクロージャを作っていた。履歴は1語あたり
最大 `WORD_HISTORY_LIMIT` 件なので、確保を作らない二重ループへ直して約4割削った。
起動時同期全体（443ms）に対して、最悪ケースでも約7%。

計算量ゲート（`scale-guard.test.mjs`）の合成データには `stats` と `srsUpdatedAt` が
無く、**新しい経路を1度も通らないまま「速い」と結論していた**（1巡目 指摘3）。

直し方も一度誤った。勝つ側の履歴が負ける側を丸ごと含む形にしたところ、
誤答の照合は最後まで走るようになったが、合流後の履歴が 20件→12件 に減って
**履歴マージ側の検査が薄くなった**（2巡目 指摘3）。

最終形は履歴を2層にした。**共有層**（両端末で同じ日時・誤答はすべてここ）が
誤答照合を最後まで走らせ、**分岐層**（端末ごとに別日時の正解）が履歴の和集合を
大きく保つ。2000語すべてで支配判定と誤答照合が最後まで走り、合流後の履歴は36件
（元の20件より重い）。そのうえで語数に対して線形にとどまることを固定した。

### 6.8 Codex によるレビュー

**実害のある指摘3件を受け、いずれも修正した。**

レビューは2巡した。1巡目で3件、その修正に対する2巡目でさらに2件の指摘を受け、
**すべて修正した**。

#### 1巡目

**指摘1（リリース阻害）— 時計が先に進んだ端末が、相手の誤答を窓の外へ追い出せる**

反例: 勝者 `correct=6, wrong=1`、履歴7件がすべて1時間先、`stage=5 mastered` /
敗者 `correct=1, wrong=1`、現在時刻の誤答、`stage=1 review`。
敗者の誤答が勝者の最古履歴より古く見えるため、勝者がその誤答を持っていなくても
証拠勝者になっていた。勝者の未来時刻は `clampSrsTs` で0になるが、
証拠判定はその前に走るため効かない。**修正前なら敗者の `review` が選ばれる**
＝新しい欠陥だった。

修正（1巡目）: 窓の除外を**勝った側の履歴が上限50件に達しているときだけ**にした。
→ **2巡目で破られた**（下記）。最終的に例外そのものを廃止した。

**指摘2 — 検証待ち（仮習得）マークが消える**

証拠で勝った側のマークだけをコピーしていたため、古い通常習得側が解答数で勝つと
負け側の `masteryVerify` が消え、未検証のまま本習得が確定していた。
修正（1巡目）: 証拠で勝った場合に限り、どちらかが検証待ちなら残す（OR）。
→ **2巡目で「それ自体が欠陥」と判定された**（下記）。最終的に元の実装へ戻した。

**指摘3 — 計算量ゲートが新しい経路を通っていない**

`scale-guard.test.mjs` の合成データに `stats` が無く、証拠判定へ入らないまま
性能を測っていた。修正: §6.7 のとおりデータを直した。

#### 2巡目（1巡目の修正に対して）

**指摘1 — 「履歴が上限50件」は切り詰めの証明にならない**

ちょうど50問解いただけの端末は一度も切り詰められていない。
反例: 勝者 `correct=49, wrong=1`・未来日時の履歴50件 / 敗者 `correct=1, wrong=1`・
現在日時の誤答。1巡目の修正では再発する。

修正: **免除そのものを廃止**した（§3.3）。負けた側の誤答が1件でも勝った側の履歴に
無ければ、証拠判定を使わない。例外が無ければ、この経路は構成的に存在しない。
50件ちょうどの反例もテストに追加した。

**指摘2 — ORにすると検証済みの端末へ古いマークが戻る**

これは私の判断ミスだった。合流結果は両端末に保存されるので、ORにすると
検証を済ませるたびに相手側の古いマークが復活し、**永久に本習得へ到達できない**。
既存コードが勝った側だけを見ているのは、このループを断つ設計だった。

修正: 1巡目の変更を取り消し、元の実装（勝った側だけを見る）に戻した（§3.4）。
検証は必ず正答数を1増やすので、検証した側は時刻でも解答数でも勝つ。
「戻さないこと」と「往復しても復活しないこと」を両方テストで固定した。

**指摘3 — 履歴マージ側の検査が薄くなった**

1巡目の修正で合流後の履歴が 20件→12件 に減っていた。
修正: 履歴を共有層と分岐層の2層にして、誤答照合（36件を最後まで走査）と
履歴マージ（合流後36件）の両方に負荷をかけた（§6.7）。

#### 3巡目は未実施

2巡目の修正に対する3巡目を依頼したが、Codex の利用上限に達して結果を得られていない。
3巡目の変更は次の3つで、いずれも**新しい挙動を足していない**:

1. 誤答照合の免除を廃止（＝証拠判定が効く場面が減り、従来判定へ落ちるだけ）
2. `masteryVerify` を 1.0.74 と**バイト単位で同一**へ差し戻し（`git diff` に差分が出ない）
3. 計算量ゲートの合成データ（テストのみ）

これに加えて §6.5 の総当たり比較で「作りうる状態の集合が 1.0.74 を超えない」ことを
確認している。上限が解除されたら3巡目を実施する。

#### 受けたが変更しなかった指摘

- 「合流後の `stats` は端末固有の解答数ではない」— そのとおりで、正しくは
  「その状態が取り込んだ解答の数」。因果の尺度としてはこれで正しいので、
  設計書の言い回しを直した（§4.6）。
- 「置換経路（取り込み・強制取得・Undo・復元）で `stats` が下がる」— §4.5 のとおり
  `learning` も同じスナップショットから同時に置換されるため、食い違いは生じない。
- 「旧版と混在する間は D2 が残る」— §4.2・§6.5 に記録済み。壊れないことは実測した。
- 「真に並行した更新で、負けた側の最新1問（『あやふや』など）が学習状態に残らない」—
  今日の時刻判定では「最後に答えた側」が勝つので、これは**判断基準の入れ替え**で
  あって新しい欠陥ではない。§4.6 に明記した。

なお Codex の環境では全体テストが一時ディレクトリ作成の `EPERM` で止まっており、
件数（596）は対象3ファイル分の観測。手元の全体実行は599件・終了コード0。

## 7. 結論

既存データの `(正答数, 誤答数)` を因果の時計として使うことで、
**スキーマ変更・移行・利用者の操作を一切伴わずに** D2 を直せる。
変更は `mergeLearningState` の分岐1つと補助関数2つに閉じており、
データの合流規則そのものには手を入れない。
