## 段階1: 同期identityの抽象化（BLOCKING#1）— **完了（2026-07-25）**

**結果**: 凍結スナップショットを無編集でpass（挙動不変を証明）。`syncState.id` の読み取りは
`syncRequestRoute` の外に0件（静的検査を恒久ゲート化）。45箇所の内訳は置換21 / 代入据え置き7 /
段階2送り17（全てUI）。本番検証: legacyのみ→正常同期、legacy+V2 active→合流200かつ編集で
`PUT ?room=… 200`。identityなしでは空の `?sync=` を送らずPUTも抑止。テスト97件green。


**目的**: `syncState.id` の直参照（45箇所）をやめ、「active V2資格情報 or legacyキー」を表す単一の真実へ集約する。

**なぜ今の状態が危険か**: `syncState.id` が事実上の同期identityになっているが、V2 activeでも設定されない。今は全ユーザーがlegacyキーを持つため露見しないだけで、identityとキーが同一視されている設計上の弱点。

**やること**:
- `syncIdentity()` を導入し、`{kind, legacyId, roomId, secret, expectedSyncId, endpoint}` を返す
- push/pull/retry/履歴/強制操作/online復帰/起動接続の全ガードとstale判定を、この1つのスナップショットから決める

**挙動不変の根拠**: 現在到達可能な状態は「legacyのみ」「legacy+V2 pending」「legacy+V2 active」の3つだけ。いずれも `legacyId` が存在するため、identity経由に置き換えても出力は同一になる。差が出るのは「legacyなしV2」＝**今は生成不可能な状態**のみ。

**ゲート（着手前に用意する）**:
1. 到達可能な3状態それぞれについて `syncEndpoint()` / `syncHeaders()` / `expectedSyncId` を固定する契約テスト
2. リファクタ後の静的検査: `syncState.id` の読み取りが identity モジュールの外に存在しないこと
3. ブラウザ実機: legacyユーザーとupgrade済みV2ユーザーで、変更前後の送信リクエストが一致

**ロールバック**: この段階単独でrevert可能（挙動不変なので戻しても誰も影響を受けない）

## 段階3: 起動時レースの解消（BLOCKING#2）— **完了（2026-07-25 / 本番検証済み）**

- IDB復元が確定するまで「新規ユーザー」判定を行わせない recovery barrier
- 4秒フォールバック側ではV2資格情報を一切発行しない
- 遅延IDBの障害注入テストを追加

### 実装

3状態の単調なバリア1つだけで発行可否を決める。非同期待ちもタイムアウトも持たない
（`initWordsnapSync` は同期関数のまま。段階5は分岐追加だけで済む）。

```
pending      … 復元がまだ確定していない（4秒フォールバック起動はここ）      → 発行不可
settled      … localStorageにもIndexedDBにも資格情報の痕跡が無いと確認できた → 発行可
inconclusive … 読めなかった／痕跡が残っている／既に資格情報を持っている      → 発行不可
```

`settled` にしてよいのは次の3つが揃ったときだけ:
**①読み取り自体が成功 ②耐久キーが存在しない ③値も残っていない**。
資格情報を既に持っている人（localStorageにある・IDBから復元できた）は `inconclusive` にする
（新規ではないので発行の前提を満たさない）。

`settleV2RecoveryBarrier` は最初の確定だけを採用（単調）。未知の値は安全側（inconclusive）へ倒す。
`v2NativeIssueAllowed()` は段階3では定義のみで、呼び出し側は0件（テストで凍結）。

**liveness は意図的に未定義のまま**にした。`idb.open` が永久に返らない等で pending のまま残っても、
「発行しない」だけでlegacy経路は従来どおり動く。期限つきで安全側へ倒す機構を足すより、
単調性を保つ方が誤りが少ないと判断した。

### 途中で見つけて直した欠陥（重要）

段階3では、実装1回に対して**3つの欠陥**が見つかった。いずれも「テストがgreenでも
検出できない」種類で、検出手段がそれぞれ違う。

#### 欠陥A: `unreadable` が本番では到達不能な死に状態だった（検出: 実ブラウザ障害注入）

最初の実装は `await idb.get(...)` が投げるかどうかで「読めなかった」を判定していた。
しかし実際の `idb.get` は **open失敗・トランザクション失敗・例外をすべて `null` に畳み、
決して投げない**。そのため `unreadable` は本番では到達不能な死に状態で、
IndexedDBが完全に壊れていてもバリアは `settled` を返していた
（＝段階5で誤発行を許す）。Node側のテストは `idb.get` を投げるスタブにしていたため
これを検出できず、**実ブラウザでの障害注入で初めて露見**した。

対処: 成否を返す `idb.getChecked(key)` を追加し、バリアはその成否で判定する
（最終形は欠陥Dの対処を経て `{ok, present, value}`）。
既存コードは `getChecked` を使わないため、この追加による挙動変化はない。
再発防止として、**本物の `idb` ヘルパを壊れた `indexedDB` の上で動かすテスト**を追加した
（スタブの性質ではなく実装の性質を検証する）。

#### 欠陥B: 読めたのに復元されなかった耐久コピーを無視していた（検出: Codex敵対的レビュー）

`recoverV2CredentialFromIdb` 内の読み取りが一時的に失敗すると、`durable === null` で
削除もせず `false` を返す。その直後の確認読みが成功して耐久コピーを見つけても、
最初の実装は `probe.ok` しか見ずに `settled` にしていた。
これは「読めなかった証拠そのもの」であり、段階5で別の部屋を発行してしまう。

対処: `probe.value` が残っていれば `inconclusive`。

#### 欠陥C: 壊れた耐久コピーを削除してから「新規」と判定していた（検出: Codex敵対的レビュー）

`recoverV2CredentialFromIdb` は不正／未activeの耐久レコードを `idb.delete` してから `false` を返す。
その後の確認読みは `{ok:true, value:null}` を見て `settled` にしていた。
**証跡を自分で消してから「この人は新規だ」と判定していた**ことになる。

最初の対処は「削除時にメモリ上のフラグを立てる」だったが、これは**2回目のレビューで否決**された。
フラグはDocumentローカルなので、レコードを消した後に再読込・別タブで起動すると失われ、
IDBも空なので `settled` に戻る。**誤発行を1起動ぶん先送りしただけ**だった。

最終的な対処: **削除をやめ、レコード自体を証跡として残す**。
残しても実害はなく（毎回 `false` を返すだけ）、後でactive資格情報を持てばそのまま上書きされる。
永続かつタブ横断で効き、追加の仕組みも要らない。

#### 欠陥D: 値が null のレコードをキー不存在と区別できなかった（検出: Codex敵対的レビュー）

`req.result ?? null` により、「キーが無い」と「キーはあるが値が null」が同じに見えていた。

対処: `getChecked` を `{ok, present, value}` にし、同じ1トランザクション内の
`count(key)` でキー自体の存在を確かめる。`settled` は `ok && !present` のときだけ。

#### 教訓

- Nodeのスタブテストは「スタブの性質」を検証してしまう。**実装の性質**（実ヘルパ・実ブラウザ）を
  検証する層が別途要る
- 「読めた」だけでは不十分で、**読めた結果が何だったか**まで見ないと安全側に倒せない
- クリーンアップ処理（削除）は、判断材料そのものを消しうる。**証跡は消さずに残す**のが最も単純で確実。
  メモリ上のフラグで代用すると、再起動・別タブで失われて「先送り」にしかならない
- 「値が空」と「キーが無い」は別物。`?? null` のような正規化はその区別を静かに潰す

### 検証

- 挙動不変の実測（4状態で旧経路と戻り値・localStorage最終状態が一致）:
  legacyのみ / 既存V2ユーザー / localStorage消失+耐久コピーあり / IDB障害 → **全て一致**。
  追加IDB読み取りは「資格情報がどこにも無い場合」のみ1回（既存V2ユーザーは0回）
- 実ブラウザ障害注入（IndexedDB openを遅延・破壊するシムを注入）:
  - 遅延6秒: 4秒フォールバックで同期開始した時点(5.8s) `pending` / 発行不可 → 確定後(7.8s) `settled`
  - IDB完全故障: 起動時から `inconclusive` / 発行不可、アプリはlegacy経路で通常起動
  - 壊れた耐久レコードを実際にIDBへ書いて**2回**再読込: どちらも `inconclusive` / 発行不可、
    レコードは削除されず残存（＝再起動・別タブをまたいで効く）。掃除後に再読込すると `settled` へ戻る
  - `idb.set(key, null)` で値nullのキーを作ると `{ok:true, present:true, value:null}`（実IndexedDBで確認）
  - 正常: 254ms で `settled`、同期開始時点ですでに確定済み
- 反トートロジー検査を2回実施。修正前の条件へ戻すと、対応する新規テストが確実に落ちることを確認
  （欠陥B/C版で2件、欠陥C/D版で2件）
- テスト131件green（段階3で新規26件）。段階1の凍結スナップショットは無編集のままpass
- 本番検証（デプロイ固有URL `56e3d33a` / SWなし）:
  - 資格情報なし → `settled` / `probe {ok:true, present:false, value:null}` / kind "legacy" /
    「同期済み・たった今」。**V2は発行されない**（段階3では発行経路が無いことの確認）
  - rawキーあり（pendingを注入。pendingは通信経路を切り替えないためサーバーに触れない）
    → `inconclusive` / 発行不可 / kind "legacy" / 同期正常。検証後に注入分は削除済み
- `getChecked` のトランザクションabort・片側失敗・両方失敗・成功順入替を実ヘルパで検証。
  解決しない実装だとテストがハングしてしまうため、期限付きヘルパで「解決しないこと」自体を失敗にした

## 段階4: 回復UX（BLOCKING#7）— **完了（2026-07-25 / 本番検証済み）**

- 保存済みフラグを **roomIdに紐付ける**（単一booleanをやめる）
- 提示条件: 「recovery-required かつ words>0 の最初の同期成功」。create時点で既に単語がある場合も即提示
- **ダウンロード/JSON書き出しのみを「保存完了」とみなす**（clipboardコピーだけでは消さない）
- ネイティブ限定。既存V2ユーザーへretroactiveに適用しない

### 実装

`wordsnap-v2-code-saved:v1` に roomId の配列を持つ（上限8・新しい方を残す・重複を作らない）。
壊れた値や不正なroomIdは「未保存」として扱う（注意が残るだけで安全側）。

```
shouldPromptV2CodeBackup(identity):
  isV2Native か → roomIdがあるか → 未保存か → words>0 か
  → **この部屋への保存が検証できたか**（lastVerifiedSyncTarget === identity.roomId）
```

**非nativeは最初の1判定で即false**。既存ユーザーは保存済みroom配列を読まない
（identity取得のためV2資格情報だけは読むが、これは元から毎回読んでいる）。

「保存済み」にするのは端末外へ出す2操作だけ:
- 「テキストで保存」
- 「JSONを書き出す」で **引き継ぎコードを同梱したとき**（同梱しないJSONは復旧手段にならない）

コピーでは保存済みにしない。貼り付け先が端末外に残る保証がないため。
未保存のままコピーしたときは、その理由を文言で伝える。

`renderV2RecoveryNotice()` を `renderAll` / `updateSyncBadge` / `renderV2CredentialUi` から呼ぶ。
条件を初めて満たしたときだけ設定とV2セクションを自動で開き、以後は注意表示が残るだけにする。

### 途中で見つけて直した欠陥

#### 欠陥A: 提示条件に「表示用の状態」を使っていた（検出: Codex敵対的レビュー）

最初の実装は `syncState.lastSyncedAt` を「同期に成功した」の判定に使っていたが、
これは**表示用**の値で、2方向に壊れていた。

- **出るべきときに出ない**: createの成功は `activateV2Credential` を通るだけで
  `lastSyncedAt` を更新しない。既に単語がある人がcreateしても、その後に変更や
  手動同期がなければ注意が永久に出ない（計画書の条件2が満たせていなかった）
- **出るべきでないときに出る**: `setSyncStatus(..., "live")` が `lastSyncedAt` を立てるが、
  **共有用リンクのコピー／共有の成功でも "live" で呼ばれる**（同期通信は一切していない）。
  同期が失敗中でも共有操作だけで注意が出て、そのまま保存すると「保存済み」になり、
  ローカルの単語がその部屋に入っていないのに注意が消える

対処: 表示と記録を分離し、**保存が検証できた保存先だけ**を記録する
`lastVerifiedSyncTarget` を導入した。呼ぶのは検証済みPUT成功とcreate成功だけ。
PUT側は**送信開始時のidentityスナップショット**で記録する（送信中に切り替わった場合に
切替先を誤って記録しないため）。提示条件は現在の `roomId` との一致を必須にした。

#### 欠陥B: 警告がグレーで表示されていた（検出: 実ブラウザでの配色実測）
`color: var(--danger-text)` を書いていたが、設定内の `p` に効く既存ルールの方が詳細度で勝ち、
`--muted` のグレーになっていた。枠線と背景だけが赤系で、肝心の文字が警告に見えない状態。
隣の `.sync-v2-code-warning` が `!important` を使っているのは同じ理由だった。

#### 教訓

- 単一ファイルの巨大CSSでは、新しいクラスの `color` が既存の詳細度に負けることがある。
  **目視でなく計算値で確かめる**（`getComputedStyle` + コントラスト比）
- **表示用の状態を判断材料に流用しない**。「ユーザーに成功と伝えた」と
  「データが実際にその保存先へ入った」は別物で、前者は共有操作でも立つ
- Documentローカルの記録は、**再構築できる経路をすべて押さえて初めて成立する**。
  段階3では「消えると危険側」だったが、ここでは「消えると抑止が永久化する」形で壊れた
- 「保存先が正しい」だけでは足りず、**そこに何が入っているか**まで確かめないと、
  空の保存先を根拠に「守られている」と見せてしまう
- **テスト件数だけを見て green と判断しない**。`npm test` の終了コードを見る
  （Nodeテストが全passでも、後続のリリースチェックが落ちていることがある）
- **似たコードへの一括置換は、周辺のローカル変数名まで確認してから当てる**。
  同じ形の分岐が複数あっても、スコープは同じとは限らない
- 「呼び出し前にスナップショット」は、**内側の関数がawaitを跨いで再評価する**なら無意味。
  結果が何を指すかは、**応答そのものから取る**のが最も確実
- まれにしか通らない分岐のReferenceErrorは、テストがgreenでも本番で壊れる。
  **識別子のスコープを字句レベルで検査する**ゲートを置く

#### 欠陥C: 再読込すると注意が二度と出なくなる（検出: Codex敵対的レビュー2周目）

`lastVerifiedSyncTarget` はDocumentローカルなので、再読込のたびに空へ戻る。
ところが記録していたのはPUT成功とcreate成功だけで、**起動時のGETで
「送信不要＝サーバーの内容がこの端末の内容を含む」と確認できた場合に記録していなかった**。
そのため、コードを未保存のまま再読込すると、サーバーに正しく保存されていても
注意が二度と出ない（＝抑止が永久化する）。

対処: 検証できる経路すべてで記録する。起動接続とJSON資格情報接続の `needsPush=false` 分岐、
強制上書きのPUT成功、強制取得の置換完了を追加した。
一方、通常pullの `changed=false` は「ローカルが変わらなかった」だけで
**サーバーとの一致を意味しない**（ローカルに未送信の追加があってもfalseになる）ため、
意図的に記録しない。

#### 欠陥D: 空のcreateを「単語が守られた」根拠にしていた（検出: Codex敵対的レビュー2周目）

保存先IDだけを記録していたため、空の状態でcreateしたあとオフラインで単語を追加すると、
サーバーには何も入っていないのに注意が出て、コードを保存すると消えてしまう。

対処: 記録に **その時点でサーバー側に入っていると確認できた語数** を持たせ、
0語なら提示しない。送信中に増えた分をその成功の保証に含めないため、
語数は **送信開始時にスナップショット**する（push・createとも）。

#### 欠陥E: 決定ゲート（npm test）が実は落ちていた（検出: Codex敵対的レビュー2周目）

`check-release.mjs` の送信キュー検査は `pushWordsnapState` をサンドボックスで実行するが、
`recordVerifiedSync` を定義していなかった。実装からの呼び出しが ReferenceError になって
catch へ入り、不要な再送タイマーが積まれて検査が失敗していた。
Nodeテスト側は151件passだったため、**私は数字だけを見て「green」と誤って報告した**。
`npm test` の終了コードは 1 だった。

対処: ハーネスへ `recordVerifiedSync` のスタブを追加し、
**正常PUTごとに1回だけ、送信時点の保存先と語数で呼ばれること**も検査に加えた。
教訓は下記。

#### 欠陥F: 既存ユーザーのlegacy起動接続を壊していた（検出: Codex敵対的レビュー3周目）

**この段階で唯一、既存ユーザーに実害が出る欠陥だった。**

`needsPush=false` 分岐は `connectV2NativeSync`（V2ネイティブ）と `connectWordsnapSync`（legacy）の
2箇所にあり、周辺コードがほぼ同一だった。私は同じ文字列置換を両方に当てたが、
保存先IDのローカル変数名が前者は `requestedId`、後者は `id` で違っていた。
結果、legacy側は `recordVerifiedSync(requestedId, …)` で **ReferenceError** となり、
catchに落ちて同期がエラー状態・切断扱いになる。

回復UXはV2ネイティブ限定なので、legacy側の呼び出しは**削除**した（記録する意味がない）。

**なぜ自分で捕まえられなかったか**: テスト158件はgreenで、ブラウザ確認もしていたが、
`needsPush=false` は「サーバーの内容がこの端末の内容を完全に含む」ときだけ通る分岐で、
通常のテスト操作では `needsPush=true`（push経由）になってしまい踏めていなかった。

**恒久ゲート化**: `recordVerifiedSync` に渡す識別子が、呼び出し元の関数内で必ず宣言されて
いることを機械的に検査するテストを追加した。まれな分岐でのReferenceErrorは
テストがgreenでも本番で壊れるため、字句レベルで潰す。
あわせて「legacy専用の起動接続からは記録しない」も固定した。

#### 欠陥G: 記録漏れ経路が3つ残っていた（検出: Codex敵対的レビュー3周目）

`joinV2Room`（合流先stateをそのまま採用）、`connectImportedV2Credential` の
`needsPush=false`、`restoreFromRevision`（force PUT成功）は、いずれも後続の
push/connectを必須としないため、非空データが保存先にあっても記録されず
注意が出ない経路になっていた。3箇所とも記録を追加した。

#### 欠陥H: force系が通信後に保存先を取り直していた（検出: Codex敵対的レビュー3周目）

`forcePushOverwrite` / `forcePullReplace` は応答後に `syncRequestRoute()` を再取得していた。
別タブがlocalStorageの資格情報を切り替えてもこのDocumentの `requestGen` は増えないため、
**通信していない保存先を検証済みとして記録**しうる。通信前にスナップショットする形へ直した。

#### 欠陥I: 記録の保存先が実際の通信先とずれうる（検出: Codex敵対的レビュー4周目）

「通信前にスナップショットする」（欠陥Hの対処）でも不十分だった。
`syncPutState` は **gzip圧縮を `await` してから** `syncRequest` を呼び、
`syncRequest` はそこで改めて `syncRequestRoute()` を評価して送信先を決める。
圧縮待ちの間に別タブがactive資格情報をA→Bへ切り替えると、
**PUTはBへ飛ぶのに記録はA**になる（別タブのlocalStorage変更ではこのDocumentの
`requestGen` は増えないため、stale判定にも掛からない）。

対処: `syncRequest` が **応答の `syncId` と照合済みの保存先** を `data.verifiedSyncTarget`
として返し、記録側はそれを最優先で使う（通信前スナップショットは予備）。
これは「実際に通信し、サーバーが同じ保存先だと答えた」値そのものなので、
呼び出し側のどのawaitを跨いでもずれない。

## 段階5: 新規ユーザーの自動V2発行（BLOCKING#5, #6, #8）

段階4までで、実装1回あたり平均2件のBLOCKINGが出た。段階5は唯一挙動を変える段階なので、
**さらに4つへ分割**し、最後の1手以外はすべて挙動不変にする。

```
5-1  identity操作の排他基盤（claim）＋ 切替時のタブ間空白期間の解消   【完了・本番検証済み】
5-2  サーバー側 kill switch（SYNC_V2_NATIVE_DEFAULT）の受付          【完了・本番検証済み】
5-3a 新規ユーザーのidentity確立を1か所へ集約（着地保証の固定）        【完了・本番検証済み】
5-3b クライアントの発行経路一式                                      【完了・本番検証済み】
5-4  本番でフラグON                                                  【完了・本番検証済み】← 唯一の挙動変更
```

**Phase 2 は 5-4 の完了をもって終了**。2026-07-26 以降に初めてアクセスした人は、
legacyキーではなくV2ネイティブの資格情報で始まる。既存ユーザーはlegacyのまま
影響を受けない（移行は本人が設定から行う）。

**5-3をaとbに割った理由**: `initWordsnapSync` は同期関数で、新規ユーザーにはその場で
legacyキーを発行していた。V2発行は非同期なので「legacy発行を保留 → V2を試す → 失敗したらlegacy」
に組み替える必要がある。保留中に例外やハングが起きると**新規ユーザーが同期の無いまま
取り残される**（サーバー保存も端末間の引き継ぎも効かず、端末を変えると単語が消えたように見える）。
そこで 5-3a で「どの経路でも必ずlegacyへ着地する」を先に固定し、5-3b でその手前にV2を挟む。
逆順だと、着地保証の無い土台に新しい分岐を足すことになる。

**5-3の意味**: 発行経路を完全に実装しても、サーバー側フラグが未設定なら毎回拒否され、
必ずlegacy fallbackへ倒れる。つまり**現行と同一の挙動のまま、fallback経路を本番で検証できる**。
新規ユーザーがV2を受け取り始めるのは 5-4 でフラグを立てた瞬間だけ。

**kill switchをサーバー側に置く理由**: クライアント定数だと無効化にデプロイが要る。
Cloudflareの環境変数なら**デプロイなしで即座に戻せる**。しかも戻した先の挙動は
5-3で本番検証済みのlegacy fallbackそのもの。`SYNC_V2_ENABLED`（create/upgrade全体）とは
独立した変数にし、段階1〜4とPhase 1の機能には一切影響させない。

### 段階5-1: identity操作の排他基盤

**解く問題**（段階3・4のレビューで持ち越した2件）:
- `switchNativeV2ToForeignLegacy` は V2資格情報を消してから legacy ID を保存する。
  その間に別タブが起動すると、identityが完全に不在に見える（＝5-4以降なら新規発行の対象）
- 新規ユーザーが2タブを同時に開くと、両方が発行条件を満たしうる

**方針**: 「identityを書き換えている最中」を表す claim を置き、
claimがある間は他タブに identity の新規決定をさせない。
claimを見た側は legacy へ倒すのではなく**何もしない**（倒すとそれ自体が別の決定になり、
V2とlegacyが同一端末に並立する）。identityが無いタブは同期しないだけで害はない（段階1で保証済み）。

**実装（レビュー後の最終形）**:
- 一次手段は `navigator.locks`（`ifAvailable`）。タブが落ちれば自動解放されるので、
  TTLにも端末時計にも依存しない。既存の `runContextGenerationOnce` と同じ方針に揃えた
- 非対応環境と、他タブへ状態を見せるために `wordsnap-sync-identity-claim:v1`
  （`{at, kind, token}`・TTL 30秒）も書く。**書いた直後に読み直すだけでは
  伝播遅延で両者勝ちになりうる**ため、60ms の沈静化を挟んでから所有者を再確認する
- **見る側**: `initWordsnapSync` で `identityDecisionDeferred = claimあり && 保存済みキーなし` を
  `startupDecision` の適用より前に算出し、**3つの決定すべて**を抑止する:
  ① URLキー(`?w=`)の永続化 ② それをメモリのidentityとして採用 ③ legacyキーの自動発行。
  claim中は `syncState.id` を空のままにし、「別のタブで変更中。終わったら再読み込みを」と表示する
  （汎用の「準備中…」だと待てば直ると誤解されるため、専用分岐にする）
- **Locks APIが例外・拒否を返す環境**では「排他できないが続行」へ倒す（`runContextGenerationOnce`
  と同じ方針）。ここで失敗にすると、Locksが投げる環境で切替が恒久に不可能になり、
  しかも「別のタブで変更中」という誤った文言が出続ける。取得失敗にするのは
  `ifAvailable` が null を返した場合＝**実際に他が保持しているとき**だけ
- `releaseIdentityClaim` は claim と lock の解放条件を揃える（自分のclaimでないなら
  lockにも触らない）。片方だけ落とすと、排他がTTL・端末時計依存のclaim側だけに退化する

**順序反転（legacy IDを先に保存してからV2を退役）を採らなかった理由**: 一時的に legacy と V2 が
並立し、段階1の経路優先則により、appStateが旧native内容のまま別タブがforeign roomへ
PUTしうる。claim方式の方が安全。

- **自分の説明とコードが食い違っていないか**を、レビュー依頼文を書くときに突き合わせる

### 段階5-2: サーバー側 kill switch — **完了（2026-07-25 / 本番検証済み）**

`?create=1&native=1` が付いたcreateだけを、`SYNC_V2_NATIVE_DEFAULT !== "1"` のとき拒否する。

**拒否の形**: `403` ＋ `{"error":"native default disabled","code":"native-default-disabled"}`。
- **503にしてはいけない**。5-3のクライアントは拒否を受けたら無言でlegacyへ倒すが、
  障害と同じ形だと再試行ループやpending滞留になる（レビュー指摘の受入条件）
- 恒常的な拒否であること（何度試しても同じ）を契約テストで固定した

**判定の順序**（テストで固定）:
1. `SYNC_V2_ENABLED !== "1"` → 503（全体停止が最優先。nativeだけ通る抜け道を作らない）
2. `native=1` かつ専用フラグ未設定 → 403（**レート上限を消費する前**。拒否のたびに枠を
   食うと、フラグを立てた直後に本来の利用者が429になる）
3. createのレート上限（10回/時/IP）

**クライアントは無変更**。`native=1` を送るのは5-3で作る自動発行経路だけなので、
この段階では誰もこの分岐に到達しない＝挙動は完全に不変。

**`native=1` はセキュリティ境界ではない**。クライアントが付けるパラメータなので、
省略すれば通常のcreateになる。これは自分たちの展開制御用のスイッチであり、
手動createはPhase 1の機能として元から開いている（レート制限つき）。

**フラグは文字列 `"1"` のときだけ許可**（fail-closed）。`"0"` `"true"` `" 1"` 等はすべて拒否。

**レビュー結果**: `GO`（BLOCKING 0件）。テスト194件green、`npm test` 終了コード0。

**本番検証**（実際にAPIを叩いて確認）:
- `?create=1&native=1` × 6回連続 → すべて `403` ＋
  `{"error":"native default disabled","code":"native-default-disabled"}`（恒常的）
- legacy同期 `?sync=…` → `200`（既存ユーザーの経路は無影響）
- 手動create（`native=1` なし）→ `200`（Phase 1の機能は生きている）

**運用上の知見**: デプロイ直後はエッジ伝播が完了しておらず、1回目は新コード・2回目は
旧コードの応答が返った。Phase 1の鍵リング投入時と同じ現象。**本番検証は数回繰り返して
収束を確認する**こと。またデプロイ固有URL（`<hash>.wordbank.pages.dev`）では
Functionsが解決せず「Deployment Not Found」になるため、APIの検証は本番ドメインで行う。

**5-3への申し送り（レビュー指摘・重要）**: 既存の手動create経路は**一般の403を
「room衝突」とみなして再試行**する（`publish/index.html` の createV2Room）。
5-3の自動発行では、
```
response.status === 403 && data.code === "native-default-disabled"
```
を**一般の403処理より先に**判定し、無言でlegacyへ倒したうえで `origin:"create"` の
pendingを破棄すること。statusだけを見ると不要な再試行が走る。

### 段階5-3b: クライアントの発行経路 — **完了（2026-07-26）**

`issueV2NativeCredential()` … 失敗したら必ず false を返す契約。
`bootstrapNewUserIdentity()` … try/catch/**finally** で、どの枝でも
`applyEstablishedIdentityToUi` → `startSyncWithEstablishedIdentity` に到達する。

ガード（すべて突然変異テストで「外すと落ちる」ことを確認済み）:
1. `v2NativeIssueAllowed()` … 回復バリアが settled のときだけ発行
2. 自らclaimを取得し、取得後に `identityClaimBlocksDecision` で再確認
3. rawキーの不在で「資格情報なし」を判定（壊れたレコードも「保存あり」扱い）
4. active化の直前にrawキーを読み直す（応答待ちの間の別タブ確定を後出しで上書きしない）
5. `403 && code === "native-default-disabled"` を他のstatus処理より先に確定。再試行ループを持たない
6. それ以外の全応答（未知4xx・413・422・429・5xx・parse失敗・通信断・タイムアウト）はlegacyへ
7. `v2Fetch` に短いタイムアウト（10秒）を渡す。通常同期の60秒とは別

**ハーネスが炙り出した欠陥2件**（どちらも静的照合では見つからなかった）:
- 応答待ちの間に別タブがlegacyキーを確定した場合、フォールバックが**それを上書き**していた。
  同じ端末の2タブが別々の保存先へ送り続けてデータが割れる。既に決まっていれば合流するよう修正。
- フォールバック中の予期しない例外で、identity未確立のまま抜ける経路があった。
  `finally` で出口を保証し、最後の手段としてlegacy発行を試みるよう修正。

**残る既知のコスト**: タイムアウトで中断した場合、サーバー側にroomが作られているのに
クライアントは資格情報を破棄するため、到達不能なroomが残る。createのレート上限（10回/時/IP）も
1消費する。新規ユーザーの語数はほぼ0なので実害は小さいが、NAT環境では上限に当たった分が
legacyへ倒れる（安全側）。

### 段階5-3〜5-4の要件（元の計画から継続）

- 「資格情報なし」判定は **rawキーの不在**で行う（壊れたレコードも「保存あり」扱い）
- active化は **200 かつ validSyncPutResponse** のみ。403の限定再試行を除き、未知4xx・413・422・parse失敗を含む**全ケースでlegacy fallback**（catch-all）
- legacy fallback確定時点で origin=create の pending を **破棄**（後日の再createで別系列に分岐するのを防ぐ）。以後V2へ移るならそのlegacyを **upgrade** する
- **独立kill switch**（`wordsnap-v2-native-default` 相当）で、ロールバックは分岐の無効化のみ。段階1〜4は残す
- NAT環境（create 10回/時/IP）で429になるE2Eを実施
- **複数タブ同時起動**を検討する（段階3で気づいた点）。バリアはページ読み込み単位のため、
  新規ユーザーが2タブを同時に開くと両方が発行条件を満たしうる。active化の直前に
  rawキーを読み直す、または発行を1タブへ直列化する必要がある
- **`retireNativeV2Credential` のタブ間空白期間**も発行排他に含める（段階3のレビューで判明）。
  退役はIDBとlocalStorageのV2資格情報を削除してから、呼出し側がforeign legacy IDを保存する。
  その間に別タブが起動すると一時的にidentityが完全に不在に見える。
  legacy IDを耐久保存してからV2を退役させる順序に変えるのが素直
