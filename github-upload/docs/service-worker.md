# Service Worker の契約と検査（2026-08-07）

`publish/wordsnap-sw.js`（104行）は本番へ配信される実コード。
このファイルだけで少なくとも4種類の実害が出ている
（冒頭コメントの版履歴がそのまま事故の記録）。

| 版 | 何が起きていたか | 重さ |
| --- | --- | --- |
| v5 | 個人キー付きURL（`?w=...`）を Cache Storage に保存していた | **秘密が端末に残る** |
| v6 | 本体の事前取得に失敗しても activate へ進み、旧キャッシュを消してオフライン起動を壊していた | アプリが開けない |
| v7 | OCRの版なしパスの残骸が端末に残っていた | 容量の無駄 |
| — | 存在しない `wordsnap-quiz.html` を precache し、配信側のフォールバックで本体を二重に持っていた | 容量の無駄 |

なかでも v5 は、リポジトリが公開である以上いちばん重い性質のもの。

## 既存の検査との関係（重要）

`check-release.mjs` にも SW の検査はあった。ただし内訳は次のとおりで、
**大半がソースの文字列一致**である。

| 既存の検査 | 方式 |
| --- | --- |
| `CACHE_NAME` が `wordsnap-v7` であること | 文字列一致 |
| 本体を先に取ってから任意ファイルを allSettled すること | 文字列一致 |
| `wordsnap-quiz.html` を参照していないこと | 文字列一致 |
| ナビゲーションのキャッシュキーを `new URL("./", scope)` にしていること | 文字列一致 |
| `cache.put(...).catch(...).then(() => response)` の並び | 文字列一致 |
| precache に必須アセットが含まれること | 文字列一致 |
| install: 本体失敗で reject・skipWaiting しない | **実行** |
| install: 任意失敗では続行し skipWaiting する | **実行** |

文字列一致は、**その並びを保ったまま流れを変える改修を素通しする**。
たとえば v5 の回帰は「`new URL("./", scope).href` という式が存在するか」
でしか見ておらず、その値を実際に `cache.put` へ渡しているかは確かめていない。

そこで `scripts/service-worker-contract.test.mjs`（`npm run test:sw` /
`npm test` に同梱）を足し、**fetch ハンドラを実際に動かして**
check-release が見ていない振る舞いを固定した。SW 本体は1行も変えていない。

新しく押さえたのは次の7点で、いずれも既存の検査には無かった:

1. GET 以外の素通し
2. クロスオリジンの素通し
3. `/api/` の素通し（**これが無いと同期の応答がキャッシュされる**）
4. 実際に書かれたキャッシュキーに個人キーが含まれないこと（v5の実行検査）
5. 個人キーが違ってもエントリが1つに集約されること
6. オフライン復帰（`ignoreSearch` 込み）
7. 静的アセットの cache-first と、失敗応答を保存しないこと、
   activate が現行以外だけを消すこと

## 固定してある不変条件

### 素通し（`respondWith` を呼ばない）

- **GET 以外**。同期の PUT を横取りすると、書き込みがキャッシュ層を通る。
- **クロスオリジン**。Datamuse・dictionaryapi.dev・翻訳・AI などは対象外。
- **`/api/`**。同期・フィードバック・テレメトリを絶対にキャッシュしない。

### 個人キーを残さない（v5 の回帰防止）

- `?w=<個人キー>` 付きURLでナビゲーションしても、`cache.put` のキーは
  scope の `./` に正規化される。キーそのものがキャッシュに残らない。
- 個人キーを切り替えても、エントリは1つに集約される（キーごとに増えない）。

### ナビゲーションは network-first

- オンラインではネットワークの応答をそのまま返す。
- オフライン（fetch が失敗）ではキャッシュ済み本体へ復帰する。
  クエリが違っても引けること（`ignoreSearch`）を別テストで押さえている。
  末尾の `caches.match("./")` フォールバックに救われて素通りするため、
  そこだけを狙った検査を分けてある。

### 静的アセットは cache-first

- キャッシュにあればネットワークへ行かない。
- 無ければ取得してキャッシュへ足す。ただし**失敗応答（404等）は保存しない**。

### install / activate

- 本体（`./`）の取得失敗は install 失敗として扱う（v6 の回帰防止）。
  失敗時は `skipWaiting()` しない。
- アイコン等の任意ファイルの失敗は握りつぶして続行する。
- activate は `CACHE_NAME` **以外**のキャッシュだけを削除し、`clients.claim()` する。
- precache に存在しないファイルを含めない。

## 検査が空振りしていないことの確認

SW をわざと壊して、テストが落ちることを**16通り**確認した。
そこへ至るまでに、**私のテスト側の穴が7件見つかっている**。
うち5件は Codex の独立レビューが見つけたもので、自分の変異テストでは出なかった。

| すり抜けた／見落としていた点 | 原因 | 見つけた者 |
| --- | --- | --- |
| GET以外の素通しを外す変異が通る | 検査を `/api/` 宛にしていたため、後段の「`/api/` 素通し」に救われていた | 変異テスト |
| `ignoreSearch` を外す変異が通る | 末尾の `caches.match("./")` フォールバックに救われていた | 変異テスト |
| `cacheName()` という未定義関数を呼んでいた | 直前の編集後にテストを回していなかった | Codex |
| `.clone()` を消す改悪を検出できない | スタブの Response が body の消費を再現していなかった | Codex |
| cache-first への改悪を検出できない | network-first の検査を**空のキャッシュ**から始めていた | Codex |
| キーごとに別キャッシュを作る実装を検出できない | 「最初のキャッシュ」しか見ていなかった | Codex |
| 素通し対象がキャッシュへ書き込む改悪を検出できない | 「`respondWith` を呼ばない」しか見ていなかった | Codex |

**「テストが通った」ではなく「壊したら落ちた」まで確認しても、まだ足りない。**
変異テストは自分が想像した壊し方しか試せないので、独立した目が要る。

過剰な縛りも1件外した。書き込み回数と順序を `deepEqual` で固定していたが、
必要な不変条件は「個人キーを含まない正規キーへ保存」「キャッシュを集約する」
であって、再検証で複数回書く実装まで落とす理由はない。

## スタブの方針

npm 依存を増やせないので、`caches` / `fetch` / `Request` / `Response` は
自前のスタブで代替している。**スタブが実物と形が違うと、壊れているのに
通るテストになる**（過去に踏んだ）。そこで、SW が実際に触る性質だけを
実物に寄せ、それ以外は持たせていない（持たせると使えてしまい、差が隠れる）。

実物に寄せてある点:

- `Cache.add` は非2xxで reject する（install の必須/任意の切り分けがこれに依存）
- `CacheStorage.match` の `ignoreSearch`
- 相対URL `"./"` の解決。実物は SW スクリプトのURLが基準になる。
  本番は `register("wordsnap-sw.js")` をルートのページから呼ぶので
  SW は `/wordsnap-sw.js`、scope は `/`。スタブもこれに合わせている。
- `event.waitUntil` / `event.respondWith`
- **`Response` の body は一度しか読めない。** `Cache.put` に渡すと消費され、
  そのままブラウザへ返せなくなる（利用者には真っ白な画面として出る）。
  スタブでも `put` が `bodyUsed` を立て、`match` は毎回あたらしい応答を返す。
  これを再現していなかったとき、`.clone()` を消す改悪が素通りしていた。

**寄せていない点（既知の限界）:**

- `Cache.add` / `Cache.put` は `206 Partial Content` も拒否するが、
  スタブは `ok` しか見ていない。このSWは Range 要求を扱わないので実害はない。
- `Vary: *` や body の locked/disturbed 状態は再現していない。
- `ORIGIN` と `SCOPE` をルート配備で固定している。カスタムドメインや
  サブパス配備へ変えるときは、このテストも一緒に直す必要がある。

## 検査していないこと

- 実ブラウザでの登録・更新・`skipWaiting` のタイミング
- 複数タブが同時に開いているときの `clients.claim()` の挙動
- Cache Storage の容量上限に達したときの挙動

## 分かっている設計上の判断

- ナビゲーションで `response.ok === false`（5xx等）のときは、キャッシュへ
  フォールバックせずエラー応答をそのまま返す。サーバー側の異常を
  キャッシュで隠さない代わりに、キャッシュがあってもアプリが開けない。
  **挙動が変わる変更なので、現時点では手を入れていない。**
- 静的アセットは `CACHE_NAME` を上げるまで更新されない。`assets/` を
  差し替えるときはキャッシュ名も上げる必要がある。
