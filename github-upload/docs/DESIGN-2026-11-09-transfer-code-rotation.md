# 引き継ぎコードの再発行と旧コードの失効 設計書

作成: 2026-11-09 / 状態: **提案・未実装（rev2: 独立レビュー反映）** / 対象: issue #79。リスク区分: **高**（同期認証・復旧・データ保全）。実装時は決定論的な契約テストと実機試験を先に行い、実装者と独立したレビュアーが差分と受入結果を確認する。

凡例: 【事実】は rev1 のコード確認、または独立レビューが GitHub main の `a95f41f` で照合した内容。【提案】は未実装の仕様。【推測】は確認できていない予測。行番号は固定の根拠とせず、実装時は関数名で再確認する。

## 結論

**同じ `room_id` のまま認証秘密 `wk_` を替える A 案を採用する。** 再発行 POST は `rooms` の認証列と世代だけを更新し、`rooms.state_key`、`states`、`state_revisions` に触れない。

**初回導入は、パスキー未連携かつ V2 ネイティブ（`upgraded_from_legacy=0`）の部屋に限る。** Web Locks が使えない環境には再発行を出さない。連携済みの部屋に必要な封筒更新と追加認証、legacy 移行済みの部屋、古い版との同時利用の保証は後段に分ける。初回に保証する旧版対策は、**旧版からの直接の V2 通信を再発行後に拒否すること**である。共有ストレージを介した旧版から新版への古い学習 state の持込みは残る（§5）。

端末は新秘密を二つの保存先に保留し、**新コードを端末外に保存したという本人の確認を保留に記録してから** POST する。起動時には active と保留の全候補を検証して結果を解決する。

## 背景と受入条件

引き継ぎコードは V2 同期先の全権限を持つ。現状、漏えいを疑った利用者がその秘密を失効させる API はない。依頼文では 2026-07-10 のレビューで P1、2026-11-06 の外部レビューでも指摘された。

初回の合格条件は、対象部屋で旧コードによる新たな V2 認証を拒否できること、新コードが同じ部屋に入れること、再発行自身が学習データを変えないこと、落下後にも端末が有効な秘密を安全に判定できること、他端末へ新コードでの再接続を案内できること。403 の判定には機能フラグと各操作のレート制限を通過したという前提を付ける（§1・§10）。

## 1. 現状と不変条件

| 項目 | 【事実】現状 | 設計上の扱い |
|---|---|---|
| V2 資格情報 | `roomId=wr_`＋32hex、`roomSecret=wk_`＋60hex。引き継ぎコードは `roomId.secret[.vaultKey]` | roomId とコード形式を維持し、secret だけ替える |
| 金庫鍵 | `wv_`＋64hex は API キー封筒用で、同期認証の `x-room-key` には使わない | `wk_` の再発行では替えない |
| サーバー認証 | `verifyRoomSecret` は鍵リングの HMAC を比較する。`updateAuthHashLazily` は読んだ旧 hash・kid を条件に再ハッシュする | 再発行も旧 hash・kid を条件に更新する |
| 現行の拒否 | 資格情報の形式不正、部屋不存在、秘密不一致は通常 403 `{error:"forbidden"}`。認証失敗枠の上限は 429。`create=1` には資格情報照合より前の `v2-create` 制限があり、機能フラグによる拒否も先行し得る | 「旧コードは 403」は、該当機能が利用可能で、操作ごとのレート制限に掛からない正常形式の V2 認証要求について確認する |
| 保存先 | `rooms` は `state_key UNIQUE`、`auth_hash`、`auth_kid`、`upgraded_from_legacy` を持つ。V2 の公開 roomId は内部 `state_key` に写される | 再発行 POST は `state_key` と学習データを変更しない |
| 端末の active | localStorage の `wordsnap-sync-credential:v2` を先に書き、IndexedDB `wordsnap/kv` へ非同期でミラーする。IDB からの復旧は localStorage に active が無いときだけ | 再発行では独立の保留と、確認付きの二重保存を使う |
| 控え済み印 | 現行 `V2_CODE_SAVED_KEY` は roomId、または roomId と `wv_` の指紋に依存し、`wk_` に依存しない | 再発行後は秘密にも束縛した新しい印だけを認める |
| 同期先の記録 | `lastVerifiedSyncTarget` と既存の別タブ停止判定は、同じ roomId の秘密変更を十分に表さない | 新版では秘密変更を検知し、再検証する |
| パスキー | `account_rooms.room_id` は一意。封筒の AAD は accountId と roomId。現行 `unlink-room` は連携先アカウントの新鮮なトークンを要求する | 連携済み部屋の再発行は初回対象外とし、後段で整合する認証と原子更新を設計する |
| legacy 入口 | `upgraded_from_legacy=1` の部屋には V2 と別の legacy 入口が残る | 初回対象外とする |

**初回の不変条件【提案】**: 再発行 POST は `states`、`state_revisions`、`rooms.state_key`、学習 state の revision を読書きしない。並行する通常 PUT がない条件では、前後の学習データと revision は同じである。並行 PUT がある試験では、再発行自身の SQL と PUT の結果を分けて評価する。

旧秘密の GET、PUT、履歴取得、`create=1` は、機能フラグと各経路のレート制限を通過した認証判定で 403 となる。429 や先行する 503 を「秘密が有効」と解釈しない。新秘密は同じ部屋へ入る。端末の未送信編集は資格情報の変更だけを理由に削除・自動上書きしない。

## 2. 方式の比較

| 観点 | A. 同じ roomId の認証秘密を更新【採用】 | B. 新 roomId を同じ state_key に結び直す |
|---|---|---|
| データ保全 | `state_key` を不変にし、再発行 POST は学習データに触れない | `UNIQUE(state_key)` のため旧行削除と新行作成が必要。入口を失う失敗点が増える |
| 端末の変更【推測】 | 同じ ID の秘密変更、保留、別タブ、控え済み印への対応が必要 | 左記に加え、部屋 ID の全参照と復旧 UI の移動が必要 |
| 旧版 PWA | 新秘密を共有ストレージから拾い得るので、再発行後の V2 ヘッダゲートが必要 | 新 ID でも古い JS が資格情報を拾う可能性があり、サーバー側の制限が要る |
| パスキーの後段対応 | 同じ accountId・roomId の封筒内容を替える | AAD、連携行、パスキー一覧の roomId も移す必要がある |

【事実】`UNIQUE(state_key)` と `bindStateKeyAlias` の構造上、どちらも学習データのキー変更は不要。変更箇所と復旧経路が少ない A を採る。旧秘密へ戻す 403 フォールバックは設けない。

## 3. API と D1

### 3.1 契約【提案】

| 項目 | 契約 |
|---|---|
| エンドポイント | `POST /api/wordsnap-state?room=wr_…&op=rotate`。legacy の `?sync=` には追加しない |
| 初回対象 | 認証済みの部屋で `upgraded_from_legacy=0`、かつ `account_rooms` に行がないこと。行があれば `ACCOUNTS_ENABLED` の値にかかわらず拒否し、何も変更しない |
| 認証 | `x-room-key` の旧 `wk_` を HMAC で照合する。形式不正・部屋不存在・秘密不一致は同形の 403。許可した Origin と `Sec-Fetch-Site` を確認するが、秘密を持つ非ブラウザ利用者への防御とは扱わない |
| 新秘密 | 端末の WebCrypto が 30 byte の乱数から生成する。JSON body は `{newSecret:"wk_…"}`、最大 1 KB。サーバーは新秘密を応答・平文保存・テレメトリに載せない。同じ秘密は 422 |
| 成功 | 200 `{ok:true,syncId:roomId,rotated:true}`、`Cache-Control: no-store`。state、rev、秘密を返さない |
| フラグ | `SYNC_V2_ROTATION_ENABLED` は既定 OFF。OFF は新たな POST のみ 503。再発行済み部屋の認証とヘッダゲートは OFF でも継続する |

加算型マイグレーションで `rooms.rotation_generation INTEGER NOT NULL DEFAULT 0` を追加する。初回の未連携部屋では **単一の条件付き `UPDATE rooms`** で認証 hash・kid・世代を更新できるため、`rotation_assertions` 表は作らない。既存部屋の世代 0 は従来の GET/PUT 契約を維持する。

世代が 1 以上の部屋には、認証後のすべての V2 GET/PUT、履歴、`create=1` で `x-wordbank-rotation-client: 1` を要求し、欠ければ 403 とする。新版は世代 0 の部屋にも送る。これは本人確認ではなく、古い JS による**直接の V2 通信**を止める互換ゲートである。ヘッダは公開値であり、漏えいしたコードを持つ者は付けられる。認証済み V2 GET には `rotationRequired: true|false` を加える。

**認証後に進行中の PUT も世代で守る。** 現行は認証後、学習 state の最終 SQL で部屋秘密を再確認しない。新版の V2 PUT は、認証時に読んだ `rotation_generation` を最終の state `UPDATE`／`INSERT` の同一 SQL 文の条件に含める。force の更新にも適用する。旧世代の PUT が再発行の commit 後に最終 SQL へ進めば 0 行となる。最新世代を再読し、世代が変わっていれば state を載せず 403、変わっていなければ従来の CAS 409 とする。state を載せる他の V2 応答も送信前に現行の認証・世代を確認する。既に始まった GET の取消しや、再発行前に確定した PUT の取消しは保証しない。legacy の SQL と応答は変更しない。

### 3.2 単一更新と競合【提案】

サーバーはフラグ、形式、専用レート制限、旧秘密、初回対象条件を調べる。新 HMAC を計算した後、**一つの SQL 文**で `rooms` の hash・kid を替え、世代を 1 増やす。`WHERE` には roomId、読み取った旧 hash・kid・世代、`upgraded_from_legacy=0`、`NOT EXISTS (該当 roomId の account_rooms 行)` を含める。`RETURNING` または変更行数で 1 行だけを成功とする。0 行なら競合または対象条件の変化として再読し、成功したふりをしない。単一文なので初回には複数文の rollback 用テーブルを要しない。

`link-room` が秘密照合後に旧秘密の封筒を差し込む競合を防ぐため、**初回導入前に**、連携行の `INSERT` を同一 SQL 文内の「照合時に読んだ `rooms.auth_hash`・`auth_kid`・世代がまだ一致する」という条件付き挿入へ変える。挿入が無視された場合は現行の部屋と既存連携行を確認してから結果を返す。これにより、連携が先なら再発行の `NOT EXISTS` が失敗し、再発行が先なら旧秘密に基づく連携挿入が失敗する。lazy rehash が先なら再発行側の旧 hash・kid 条件が失敗するので、再読・再照合へ進む。

`states` と `state_revisions` への SQL は再発行処理に含めない。D1 上の単一文 CAS と PUT の最終世代条件を契約試験で確かめる。

### 3.3 応答、結果解決、レート制限【提案】

POST は旧秘密を失効させるため、同じ POST の再送に 200 を返すサーバー冪等性は約束しない。端末は §4 の保留にある旧・新秘密と両 active を区別し、GET の**認証結果だけ**で現在有効な候補を確かめる。取得した学習 state はこの検査で適用しない。429、503、通信失敗は無効判定ではない。再送するときは同じ新秘密を使い、本人による再確認を要求する。

| 応答 | 端末の扱い |
|---|---|
| 200 | 新秘密で GET を確認してから active を確定する |
| 400 / 413 / 415 / 422 | 入力不正を表示。保留を無条件に消さず、候補を検証する |
| 403 | 新秘密を検証する。旧秘密を自動復活させない |
| 409 `rotation-raced` | 全候補を検証する。有効候補がなければ新コードまたはパスキーによる復旧へ |
| 429 | 保留を保持する。秘密の有効性は未確定 |
| 503 | 保留を保持する。フラグ OFF だけで既存の通常同期は止めない |

専用 `v2-rotate` は IP あたり **5 回/時を初期案**とし、成功・失敗とも消費する。失敗 HMAC は既存の認証失敗枠にも算入する。既存の `rate_limits` を使い、再発行に限ってレート制限用 D1 障害時は fail-closed の 503 とする。数値の最終決定は §13 に残す。

## 4. 締め出しを防ぐ端末の確定手順【最重要・提案】

### 4.1 排他、保留、所有権

再発行と起動時の結果解決は、**同じ roomId の Web Locks 排他**で行う。新版の資格情報更新もこの排他を使い、通常同期は開始時の資格情報・世代を固定して世代変更を検知する。UI での端末外保存待ちはロックを解放してよいが、再開時は取り直して保留の所有権を確認する。POST 中と確定処理中はロックを保持する。既存の `acquireIdentityClaim` は 30 秒で失効するため、再発行の排他・所有権の根拠にしない。**Web Locks がない環境では再発行を表示・実行しない**。通常同期の可否は §4.4 に従う。

保留専用キー `wordsnap-v2-rotation-pending:v2` を localStorage と IDB に置く。内容は `{operationId, roomId, oldSecret, newSecret, vaultKey, origin, provenance, phase, savedOffDevice, startedAt, version}` とする。`operationId` は操作ごとの十分長い乱数で、`savedOffDevice` は操作 ID と新コードの指紋に束縛した本人の確認記録とする。`phase` は `prepared`、`confirmed`、`sent` などの手掛かりであり、サーバーの結果より優先しない。秘密を含むためログ・計測に載せない。時刻は表示に使えても、候補の優先順位や所有権には使わない。

両保存先が空、または**同じ操作 ID・同じ内容**の場合だけ新しい保留を書ける。別操作の保留を上書きしない。保存、段階更新、active 確定、削除の直前にロックと操作 ID・version・内容の一致を読み直す。IDB の削除は同一トランザクションで内容を照合する `deleteIf` 相当とし、localStorage もロック内で一致を確認してから削除する。片側だけ削除に成功した場合も、残るコピーを次回検査する。

**両コピーが異なる場合は、時刻で片方を選ばない。** 両方の旧・新秘密を候補として保持し、§4.3 の結果検証が終わるまで書換え・削除・新たな再発行をしない。

### 4.2 POST 前と確定

1. 現在の active と未送信編集を固定する。`stopSyncPolling` と `bumpSyncRequestGen` で送信予約を止め、保存途中の端末データを保護する。再発行自身は学習 state を変更しない。
2. 新しい `wk_` を生成し、`prepared` の保留を **IDB と localStorage の両方へ保存して読戻す**。標準の active は旧秘密のままにする。片方でも確証がなければ POST しない。
3. 新コードを表示し、端末外への保存手段を示す。コピー操作だけでは控え済みとしない。利用者が端末外保存を明示的に確認したら、その確認を該当 `operationId` と新コードの指紋に束縛し、両保存先へ記録・読戻しする。未確認の保留では POST しない。
4. 排他と保留の所有権を再確認し、`sent` を両保存先へ記録・読戻ししてから POST を一度送る。応答喪失時は候補 GET で解決する。再起動後は**結果確認だけを自動実行**し、旧秘密が有効でも自動 POST しない。再送には本人による同じ新コードの端末外保存の再確認を要する。
5. 新秘密の GET が成功したら、先に IDB active を新秘密で書いて読戻し、次に localStorage active を書いて読戻す。両方が確定するまで完了表示をしない。新 GET の state はこの手順では適用しない。
6. 当該 roomId の旧 `V2_CODE_SAVED_KEY` 印を無効化して読戻し、再発行済み印を別キーで両保存先に記録・読戻す。新版は再発行済み印、または GET の `rotationRequired=true` があれば旧形式印を認めず、**roomId・新 `wk_`・`wv_` の指紋**に束縛した新形式印だけを認める。`lastVerifiedSyncTarget` などの成功記録を消し、別タブへ秘密変更を通知する。その後に保留を条件付きで削除する。最後に新コードを表示し、利用者が実際に保存した操作でのみ新形式の控え済み印を付ける。

### 4.3 起動時・手動復旧時の候補解決

起動時は `recoverV2CredentialFromIdb`、`bootstrapNewUserIdentity`、通常同期より先に、ロックの下で読める active と保留を集める。候補は localStorage active、IDB active、各保留の旧秘密と新秘密、利用者が入力した新コード、パスキー復旧で得た秘密である。同じ roomId の候補を個別に GET で検証し、**全候補の結果が確定するまでは保留を時刻や保存先だけで選ばない**。429、503、通信失敗があれば保留の終了判定を延期する。

| 確定した結果 | 処理 |
|---|---|
| 保留の新秘密が有効 | その保留の操作 ID を確認し、§4.2 の active 二重保存と印の無効化を完了する |
| active が有効で、保留の旧・新秘密がともに無効 | 後続の再発行で古い保留が置き換わった状態。active を維持し、全コピーが検査時の内容と一致する場合に限り古い保留を条件付き削除する |
| 入力コードまたはパスキーで得た秘密が有効で、同じ部屋の保留候補がすべて無効 | 復旧した秘密を active として安全に確定した後、古い保留を条件付き削除する。`startedAt` は判断に使わない |
| 保留の旧秘密だけが有効で、`sent` 前 | POST 未実行として、本人が継続または取消しを選ぶ。継続には端末外保存の確認が必要 |
| 保留の旧秘密だけが有効で、`sent` 以後 | 通常利用できる active があれば同期を続けられるが、保留を残し新たな再発行を禁止する。再送は本人の再確認後に同じ新秘密で行う |
| 有効候補なし、または結果未確定 | 自動の資格情報切替・新規発行・POST を止め、新コード入力、パスキー復旧、JSON 退避を案内する |

異なる二つの保留でも、全候補を検証して現在有効な秘密を一つに確定できれば上表で処理する。内容の破損、同じ操作 ID の不一致、複数の相反する成功など、結論を出せない場合は保留を残し、通常同期の可否を §4.4 で判断する。古い保留だけを消して空部屋を作らない。

### 4.4 保留領域の読取失敗と通常利用

保留領域を読めない、または両コピーの整合を確認できない状態では、**新規 V2 発行・再発行・保留の削除を禁止**する。一方、active の秘密を通常の V2 GET で明示的に検証できた既存利用者は、その active で通常同期を続けられる。未確認の保留を根拠に active を上書きしない。active が無効または検証不能なら同期を停止し、手動復旧を案内する。IDB の一時障害だけで、検証済み active の利用者を恒久的に止めない。資格情報がない状態でも、保留の読取失敗を「新規ユーザー」とみなして自動発行しない。

### 4.5 落下点

| 落ちた位置 | 端末・サーバーの状態 | 再起動時の扱い |
|---|---|---|
| 保留の書込前 | 旧 active が有効 | active を検証して通常利用 |
| 保留の片側書込中 | POST 未送信。片側に保留があり得る | 読める候補を検証。両側保存が確定するまで POST 禁止 |
| 両側保存後、端末外保存の確認前 | 旧 active と `prepared` 保留 | 結果確認のみ。確認を記録するまで POST 禁止 |
| 保存確認後、`sent` 記録前 | 旧 active と確認済み保留 | 結果確認のみ。継続時は本人の再確認を要求 |
| `sent` 記録後、POST 中・応答喪失 | 旧または新秘密が有効 | 全候補を検証。旧だけ有効でも自動 POST しない |
| commit 後、IDB active 更新前 | 新秘密と保留が有効 | 新 GET を確認し、active の二重保存を完了 |
| IDB active 更新後、localStorage 更新前 | 両 active が食い違う | 両候補を検証し、有効な新 active を localStorage にも確定 |
| active 更新後、印の無効化・保留削除前 | 新 active と保留、旧印が残り得る | 印を無効化し、保留を条件付き削除。控え直しを要求 |
| 両 active 更新・保留削除後 | 新 active のみ | 検証後に通常同期 |

localStorage と IDB の両方、端末外の新コード、利用可能なパスキー復旧経路がすべて失われた場合は、端末内だけでは復旧できない。

## 5. 別端末・旧版 PWA・未送信の編集

【事実】現行クライアントは 401/403 を一般エラーとして扱い、失効専用の停止処理を持たない。同期要求は active を localStorage から読み直すため、古いタブが新秘密を拾うことがある。さらに旧タブは、直接 PUT が 403 でも共有のローカル保存先へ古い学習 state を書ける。新版がその state を読み、通常マージ後に新ヘッダ付きで PUT する経路がある。`mergeWord` の `meaning` はローカル優先なので、遠隔で訂正された意味を巻き戻し得る。

【提案】新版は V2 の GET/PUT/履歴で 403 を受けたら、その部屋の自動 push・pull・ポーリング・409 再送を停止する。ローカルの単語、未送信変更、退避は保持する。`create=1` や legacy へ自動フォールバックしない。429、503、オフラインは失効扱いにしない。表示は「この端末の引き継ぎコードは使えなくなりました。新しいコードを入力してください。手元の単語は消していません」とし、コード誤りや部屋不存在を「再発行済み」と断定しない。

**新コードでの再接続**では先に GET で検証し、同じ roomId でも資格情報変更として送信・保存を止める。未送信変更がないと確認できた場合だけ通常同期を再開する。未送信変更、ゴミ箱、保存失敗、世代不明があれば、既存の `recoveryBeforeReplace` の 3 択と IDB 退避を共用し、「復旧先を採用」「この端末にしかない語を追加」「やめる」を提示する。退避に失敗したら中止する。「語を追加」は復旧専用 CAS で行い、409 の通常自動マージは使わない。既存語の編集、削除記録、ゴミ箱、単語帳名の差分は自動で取り込まれないと明示し、JSON 退避を提供する。

**初回の旧版保証は直接 V2 通信の遮断まで。** 古いタブによる共有ストレージ経由の古い state の持込みは防げない。再発行前に他タブを閉じ、他端末のアプリを更新する案内を出す。旧版との安全な同時利用を保証するには、確定後の保存先を旧版が書けないキーに分けるなど、保存元を識別する別設計が必要であり、初回受入条件には含めない。

## 6. パスキーとアカウント

**初回は `account_rooms` に行がある部屋を必ず拒否する。** `ACCOUNTS_ENABLED=0` でも過去の結びつき行が残っていれば拒否する。端末の「連携済み」印だけで判定せず、サーバーの行を条件付き更新の中でも確認する。§3.2 の `link-room` 競合防止は初回の前提である。

後段で連携済み部屋を扱う場合は、**旧 `wk_` と、連携先アカウントの新鮮なパスキートークンの両方**を要求する。トークンの accountId が `account_rooms` の accountId と一致することをサーバーで確認し、行の一致を原子的更新の条件にも含める。不明・不一致の結びつきでは再発行を拒否する。`unlink-room` も現行どおり連携先アカウントの新鮮なトークンを要求し、部屋秘密だけで解除できる経路は作らない。bearer 秘密だけでは、同じ秘密を持つ二者のどちらが本人か判定できないためである。

連携済み部屋の実装では、同じ accountId・roomId を AAD に使って新秘密を再封筒化し、部屋認証と封筒を一つの原子的操作で更新する。`link-room`、`recover-room`、`openWithRewrap` との並行条件、D1 batch の制約失敗時の rollback を別途契約試験で固定する。`ACCOUNTS_ENABLED=0`、KEK 不備、結びつき不明の状態で古い封筒を残したまま成功を返さない。運営が本人のパスキーや有効なコードなしに新秘密を発行する裏口は設けない。

## 7. 金庫鍵と旧方式からの移行

**`wv_` は再発行で替えない。** 認証秘密 `wk_` の漏えいを止める操作であり、`wv_` まで替えると既存の AI キー封筒を復号できなくなる。3 要素コードには現在の `wv_` を含める。2 要素コードへ金庫鍵を勝手に追加しない。金庫鍵も漏れた疑いがある場合は、API キーを発行元で変更する案内を出す。金庫鍵の再暗号化は別設計とする。

**同じ部屋へ戻る端末の金庫鍵を保持する。** パスキー復旧または新コード入力で新 `wk_` の GET が成功し、`roomId` が端末の旧 active と一致する場合、秘密が違っても端末に残る `wv_` を新 active へ引き継ぐ。現行 `recoverWithPasskey` の「roomId と secret の両方が一致した場合だけ保持」という条件を変える。2 要素の新コード入力でも同じ規則を使う。3 要素の入力コードに異なる `wv_` がある場合は黙って上書きせず、鍵の相違を示して利用者に確認させる。別 roomId へは旧金庫鍵を自動で移さない。

`upgraded_from_legacy=1` の部屋は**初回対象外**である。後段で対応しても、V2 コードの再発行だけでは旧 `?sync=<legacyKey>` 入口は失効しない。legacy のみを使う旧版は同じ学習 state を書き得るため、後段でも V2 入口の失効と legacy 入口の扱いを分けて設計・表示する。初回に「旧方式も止まる」とは案内しない。

## 8. 画面と文言【提案】

設定の「データの保存・引き継ぎ」に「引き継ぎコードを再発行」を置く。対象はサーバーで確認し、未連携・V2 ネイティブ以外には実行を許さない。Web Locks 非対応環境では再発行を出さず、通常同期は §4.4 に従う。確認画面には、他端末で旧コードが使えなくなること、未送信編集、他のタブを閉じること、**端末外へ新コードを保存してから送信すること**を示す。押し間違い防止には、iOS standalone で不安定な `window.confirm` に依存しない。

操作中は「新しいコードを端末に保留しました」「端末外への保存を確認しています」「旧コードを停止しています」「新コードで接続を確認しています」と段階表示する。端末外保存の明示確認を保留に記録できるまで送信しない。コピーだけで控え済み印を付けない。完了後はコピー・テキスト保存・iPhone パスワード保存を提示し、実際の保存操作で新形式印を付ける。結果未確定時に「保護済み」「完了」と表示しない。

完了文案:「新しい引き継ぎコードを発行しました。前のコードでは同期できません。他の端末ではアプリを更新し、新しいコードを入力してください。端末だけにある変更は再接続時に確認します」。

失敗文案:「結果を確認中です。有効なコードを確かめるまで、この端末の資格情報を切り替えません。単語は残しています」。

旧版向け案内:「アプリを最新版に更新してから新コードを入力してください。古い版では接続できないことがあります。更新前に端末の単語を JSON で控えてください」。

## 9. 脅威・限界と対策

| 脅威 | 対策と残る限界 |
|---|---|
| 漏れた旧コードによる新たな V2 GET/PUT | HMAC を置換する。機能フラグ・レート制限を通過した旧秘密の認証は 403。既に読まれた内容は取り戻せない |
| 攻撃者が未連携部屋の旧コードで先に再発行 | 初回は bearer 秘密で再発行できるため、本人の締め出しは残る。端末外の新コードと保留で正規利用者の操作失敗を防ぐが、攻撃者との本人判定はできない |
| 応答喪失・端末クラッシュ | 二重保留、操作 ID、全候補の GET 検証で解決する。旧秘密の猶予期間は設けない |
| 並行再発行・lazy rehash・連携 | `rooms` の hash・kid・世代 CAS、未連携条件、`link-room` の条件付き挿入で競合を判定する |
| 旧版 JS の直接 V2 PUT | ヘッダゲートと最終 PUT の世代条件で、再発行後の直接書込みを拒否する |
| 旧版 JS の共有ストレージ書込み | 旧タブが古い state をローカルに残し、新版が読み込んで PUT する経路は残る。旧版との同時利用の安全性は初回に保証しない |
| 金庫鍵の漏えい | `wv_` は替えない。AI キー側の変更を案内する |
| legacy 個人リンク | 初回対象外。後段でも legacy 入口を別に扱う |
| 配信物や同一オリジンの侵害 | 配信された JS は端末の秘密を読める。本機能では防げない |

## 10. 計測・テスト計画

初回の計測は匿名の固定分類だけに絞る。roomId、`wk_`、`wv_`、保留内容、パスキー ID を送らない。最低限、開始・成功・結果未確定・失効 403 の件数を確認する。詳細な成功率分析、最終変更時刻表示、専用の無期限イベント表は後段とする。既存の保持期間と送信前の伏せ字規則を守る。

**サーバー契約テスト**: 初回対象と対象外（連携済み、`upgraded_from_legacy=1`）を分ける。旧コードの GET/PUT/履歴/`create=1` が、機能フラグと各操作のレート制限を通過した認証判定で 403 になることを確認する。`create=1` の `v2-create` 429、認証失敗枠の 429、専用 `v2-rotate` 429、フラグによる 503 は別ケースとする。新コードは同じ roomId・state・revision・history に入る。世代 0 はヘッダなしで従来どおり、世代 1 以上はヘッダなしで 403、POST フラグ OFF でも新コードの通常同期は続くことを確認する。

単一 UPDATE の 0 行、並行する 2 POST、lazy rehash、`link-room` との順序競合、旧 PUT の「認証通過→再発行 commit→state 最終 SQL」、state を載せる 409 応答を試す。並行 PUT がない試験では `states` と `state_revisions` の行内容・件数を前後比較する。並行 PUT がある試験では再発行 SQL の変更対象と PUT の確定順を分け、再発行前後の単純な全体一致を要求しない。

**端末状態遷移テスト**: §4.5 の各落下点、両保存先の保留不一致、別操作 ID、条件付き削除の失敗、片側の読取不能、`sent` 後の応答喪失を注入する。未確認の保留から POST しないこと、起動時に自動 POST しないこと、active が明示的に有効なら保留領域の障害だけで通常同期を止めないこと、無効 active から空部屋を自動生成しないことを確認する。控え済み印、別タブの秘密変更、403 と 429/503 の区別、3 択と JSON 退避、同じ部屋へのパスキー復旧・2 要素コード入力時の `wv_` 保持も試す。

**2 端末の受入**: 対象部屋で A が端末外保存を確認して再発行し、学習データ・rev が不変であることを確認する。B の旧 V2 コードによる直接 GET/PUT を拒否し、B の未送信語が残ることを確認する。B を最新版に更新して新コードを入力し、必要な語だけを復旧専用 CAS で追加する。旧版タブの共有ストレージ経由の反例は残存リスクとして再現・記録し、初回の保証に含めない。実装者と別のレビュアーには目的、受入条件、関連差分、必要ファイル、テスト結果を渡す。

## 11. 段階導入と戻し方

| 段階 | 初回に行うこと | 合格条件・戻し方 |
|---|---|---|
| A. マイグレーション | `rooms.rotation_generation DEFAULT 0` を加算する。`rotation_assertions` は作らない | 世代 0 の既存 V2 同期を確認する。列は残してよい |
| B. サーバー先行 | 未連携・V2 ネイティブの対象判定、単一認証・世代 CAS、`link-room` の競合防止、最終 PUT の世代条件、旧版ヘッダゲートを配信する。POST フラグは OFF | POST は 503。既存同期は継続。問題があればフラグを OFF のまま修正する |
| C. 新クライアント | 全 V2 経路へのヘッダ、Web Locks 排他、保留・復旧、端末外保存確認、403 停止、新コード再接続を配信する | Web Locks 非対応では再発行を出さない。既存同期と手動復旧を確認する |
| D. 限定 ON | 隔離した対象部屋と 2 端末で受入後、本番の対象部屋へ拡大する | 旧コード拒否、新コード接続、落下復旧、学習データ不変を確認。不具合時はフラグ OFF で新たな再発行だけ停止する |

初回はパスキー復旧 Phase C の完了や `ACCOUNTS_ENABLED=1` を前提にしない。**連携済み部屋はフラグの値にかかわらず対象外**とする。既に再発行された部屋の世代とヘッダゲートはフラグ OFF 後も維持し、旧秘密を再有効化しない。古いサーバーへの単純な巻戻しでゲートや最終 PUT 条件を外さず、必要なら前進修正する。

**後段に残すもの**: 連携済み部屋の追加パスキー認証と封筒の原子更新、legacy 移行済み部屋と個人リンクの扱い、旧版との同時利用を安全にする保存先の分離、詳細な計測と最終変更時刻表示。初回の「旧版対策」は直接 V2 通信の遮断に限る。無料運用を維持するため、学習 state の全件コピー、新たな課金サービス、無期限イベント表は作らない。【推測】初回の再発行は低頻度の D1 操作で収まるが、無料枠の現行上限と実使用量は本番 ON 前に確認する。

## 12. 実装時の確認点

1. `link-room` の条件付き挿入と再発行の `NOT EXISTS` 条件が、どちらの確定順でも古い封筒を残さないことを試す。
2. V2 PUT の通常更新・force 更新・欠損 state の扱いで、最終 SQL に認証時の世代条件を入れる。state を載せる V2 応答も失効要求へ返さない。
3. `x-wordbank-rotation-client` を通常同期、履歴、合流、強制取得・上書きなど、すべての V2 リクエストで送る。直接 fetch を行う経路も点検する。
4. 起動時の候補検査を通常同期・自動発行より先に置く。ただし保留領域の読取失敗と、検証済み active の通常利用を分ける。
5. 保留の操作 ID と条件付き削除、端末外保存の確認記録、Web Locks 非対応時の非表示、パスキー復旧・新コード入力時の `wv_` 保持を実機で確かめる。
6. 後段で連携済み部屋を実装する際は、封筒と認証の原子更新、D1 batch の制約失敗時 rollback、解除と再発行のアカウント一致条件を別の受入条件として固定する。
