## 1. 直す問題（現行 1.0.78 で再現を確認済み）

`mergeLearningState`（`publish/index.html` 20636行）は `srsUpdatedAt`（各端末の `Date.now()`）
の大小だけで勝敗を決める。`clampSrsTs`（20648行）は**未来**を主張する端末しか弾けず、
**遅れた時計**には構造的に無力。その結果、解答数の少ない端末が「新しい」と誤認されて
進んだ端末の学習状態を上書きする。

実コード（`applyLearningResult` / `mergeWord`）をそのまま動かした実測:

| | 状態 | 次の復習まで |
|---|---|---|
| 端末A（時計が55分遅れ・6回正解） | `stage=6 streak=6 mastered` | 60日 |
| 端末B（正常・1回正解） | `stage=1 streak=1 review` | 1日 |
| **合流結果（左右どちらでも同じ）** | **`stage=1 streak=1 review`** | **1日** |

**60倍の過剰出題。** 6回分の学習成果が、1回しか解いていない端末に消される。
データ（単語・成績・履歴）は失われず、常に「出しすぎ」の方向に倒れるが、
同期のたびに繰り返し起こりうる。

## 2. 過去2回の失敗（同じ道を通らないための要約）

### 1回目: 「正解では段階が下がらない」保護（`da618eb` で取り消し）

`srsStage` は誤答時の `-2` でしか下がらない、という不変条件を根拠に「勝った側が
誤答でないなら段階を後退させない」保護を入れた。取り消した理由は、
**(a) 時計ずれ と (b) 誤答で正当に降格したあと正解した状態が、データ上まったく
同じ形（新しい側の段階が低い）で現れて区別できない**こと。保護は (b) を壊し、
「忘れた語が復習に戻らない」というより重い害を生んだ。

### 2回目: `(stats.correct, stats.wrong)` を因果の時計にする（1.0.75〜1.0.76、1.0.77 で全面撤回）

「解答処理は1問につき必ず `stats` を1増やし `applyLearningResult` を呼ぶ。
だから `stats` はその端末が適用した解答数だ」という観察に基づいた。
**この前提は合流を1回でも経ると崩れる。** `mergeWord`（20582行）が

```js
correct: Math.max(localWord.stats.correct, remoteWord.stats.correct, historyCorrect)
```

で `stats` を**履歴の和集合の件数まで底上げする**一方、`learning` は片側の丸写し
（20608行）なので、両者が乖離する。

| | stats | learning |
|---|---|---|
| 端末A（4回正解） | 4正 | stage=2 streak=4 |
| 端末B（4回正解） | 4正 | stage=2 streak=4 |
| **合流結果AB** | **8正**（架空の実績） | stage=2 streak=4（4回分のまま） |
| 端末C（実際に7回正解） | 7正 | stage=3 streak=7 |
| C と AB の合流 | — | `8≧7` でABが勝ち → **Cの進捗が巻き戻る** |

多角レビューで15件の指摘、うち本番の学習データに関わる重大なものが9件。
すべてこの1つの根から出ていた。

### 導かれる原則

1. **合流で底上げされる値（`stats`・履歴件数）を因果の時計に使わない。**
2. 片側の状態だけから善悪を判定する保護を入れない（(a) と (b) を取り違える）。
3. 単発のマージだけを検査しない。**複数往復での収束と可換性**を必ず固定する。
4. 個別の指摘を塞ぎ続けているときは、前提そのものを疑う。

## 3. 素朴な解法は誤り（実装前に検算した）

「`learning` に解答カウンタを1つ持たせ、多い方を勝たせる」は自然に見えるが**不十分**。
数値で確かめた結果:

| 場面 | 単純カウンタ |
|---|---|
| (a) 時計ずれで6回分が消える ← 直したい | ✅ 直る |
| (b) 誤答による正当な降格 ← 守りたい | ✅ 守れる |
| (c) 両端末の解答数が同じ | 決められず従来の時刻判定へ＝**D2が残る** |
| **(d) 解答数の多い側が、相手の誤答を知らない** | ❌ **相手の「忘れた」が捨てられる** |

(d) の具体例: 端末Aが5回正解、端末Bが1回誤答。**どちらの解答も相手は知らない
（並行）**のに、数の多いAが勝ち、Bで起きた降格が消える。これは1回目の失敗で
取り消したのと同じ害。

**原因**: スカラー1つでは「AはBの見たものを全部見た上でさらに進んでいる」（因果的支配）と
「AとBは別々のことをした」（並行）を区別できない。**前者だけがAを勝たせてよい条件。**

## 4. 設計: 端末ごとの計数（版数ベクトル）

### 4.1 持たせるもの

`learning.v` に、**端末ごとの解答回数**を持つ。

```js
learning.v = { "<clientId>": <その端末がこの語に適用した解答数>, ... }
```

- 鍵は既存の `clientId`（`wordsnap-client:v1`。端末ごとに自動生成される安定ID。
  localStorage が消えた場合に備えて IndexedDB に控えがあり、復元される）。
  **新しい識別子は作らない。**
- 値は `applyLearningResult` が呼ばれるたびに、その端末の成分だけを +1 する。
- **一度も解答していない語には `v` を付けない**（既定は「主張なし」）。

### 4.2 合流の規則

`mergeLearningState(a, b)` の先頭に、時刻判定より**前**に置く。

```
支配関係:  A ⊒ B  ⟺  すべての端末 d について  A.v[d] ≥ B.v[d]
```

| 条件 | 動作 |
|---|---|
| `A ⊒ B` かつ `A.v ≠ B.v` | **Aを丸ごと採用**（Aは Bの解答をすべて取り込んだ上でさらに進んでいる） |
| `B ⊒ A` かつ同様 | Bを丸ごと採用 |
| 支配関係なし（並行） | **既存の保守的マージへ落とす**（誤答があれば `review`、`srsStage` は最小、`nextReviewAt` は最小） |
| 両方 `v` を持たない | 既存の処理をそのまま（挙動を変えない） |
| 片方だけ `v` を持つ | **支配とみなさない**＝並行扱い。`v` の無い側は「主張なし」であって「0回」ではない |

合流結果の `v` は**成分ごとの最大値**（`{d: max(A.v[d], B.v[d])}`）。
これは底上げではない: 各成分はその端末が実際に適用した解答数であり、
合流しても端末をまたいで足し合わされない。前案が壊れたのは `stats` を
「履歴の和集合の件数」まで引き上げていたためで、ここにはその経路がない。

### 4.3 なぜこれで (a)〜(d) が正しく分かれるか

| 場面 | ベクトル | 判定 |
|---|---|---|
| (a) Bが**Aの学習を知らずに**1回解いた | A={devA:6}, B={devB:1} | **並行** → 保守的マージ。60倍の巻き戻りは起きない |
| (a') Bが**Aの学習を取り込んだ後に**1回解いた | A={devA:6}, B={devA:6,devB:1} | **B ⊒ A** → B採用（正しい。Bが本当に新しい） |
| (b) 降格した側が相手の解答を全部持つ | A={devA:6}, B={devA:6,devB:1} | **B ⊒ A** → 降格が守られる |
| (d) 多い側が相手の誤答を知らない | A={devA:8}, B={devB:1} | **並行** → 保守的マージ。誤答があるので `review` になり、「忘れた」が守られる |

**(a) は完全にAの状態へ戻るわけではない**（保守的マージなので `stage` は小さい方に倒れる）。
それでも 60日→1日 という壊滅的な巻き戻りは起きず、かつ Bの解答も捨てない。
**「出しすぎ」側へ倒すのは既存の設計方針と一致する。**

### 4.4 サイズへの影響（本番データで実測）

本番の実データ（9,701語 / rev 179）で測った。測定モデルの妥当性は、
計算値 412KB に対し D1 の実測値 411KB が一致することで確認済み。

| | 保存形式のサイズ |
|---|---|
| 現状 | 412 KB |
| ベクトル追加後（1〜3台） | 413〜414 KB（**+0.3〜0.4%**） |

**解答済みの語は 115語 / 9,701語（1.2%）しかない**ため、増加はごくわずか。
将来すべての語を解き終えた場合の上限はおよそ +20%（+84KB 程度）。
`test:scale` の計算量ゲートにかかる規模ではないが、実装時に確認する。

## 5. 移行と互換性

### 5.1 スキーマ版を上げる

`normalizeLearning`（19082行）は**ホワイトリスト方式**で、知らないフィールドを捨てる。
つまり旧版クライアントが一度でも保存すると `v` が消える。したがって:

- クライアント `LEARNING_SCHEMA_VERSION`: **1 → 2**
- サーバー `HIGHEST_LEARNING_VERSION`（`functions/api/wordsnap-state.js` 81行）: **1 → 2**

サーバーは既に一般化された判定を持っている（957行、`incomingLearningVersion <
storedLearningVersion` なら `409 downgrade_conflict`）。**新たな配送機構は不要。**

### 5.2 利用者に起きること

旧版のタブ・キャッシュ済みHTMLからの保存が 409 で拒否され、
「アプリが古いため保存できません。ページを開き直して最新版に更新してください。」
と表示される。**再読込すれば解消する。データは失われない**（サーバー側の最新状態が
409 応答に同梱されて返る）。

### 5.3 既存データの扱い

- 既存の `learning` には `v` が無い。**一括変換はしない**（`stats` からの初期化は
  前案が壊れた原因そのもの＝底上げされた値なので絶対に使わない）。
- `v` が無い状態同士の合流は**現行とまったく同じ挙動**にする。つまり移行直後は
  「直っていないだけで、壊れてはいない」。解答するたびに `v` が育ち、
  両端末が新版になった語から順に D2 が解消していく。
- D1マイグレーションは**不要**（サーバーは state を不透明な塊として扱い、
  単語の中身を解釈しない）。

## 9. リプレイ案の検証（2026-08-11・不成立）

「`learning` を合流するのをやめ、合流後の `history` から再計算する」案を、
実装前に実データと実コードで検証した。結論は**不成立**。

### 9.1 前提条件は2つとも満たされていた

本番の全ユーザー行（`states` 119行）で測定した。

| 懸念 | 実測 | 判定 |
|---|---|---|
| 履歴は1語50件上限。上限に達した語は最初から再計算できない | **最長8件。上限到達 0語** | ✅ 問題なし |
| `at` は端末時計依存。並び順が狂っていないか | 逆行240件だが、**すべて3つのサンプル行**（867〜1679バイト・rev2）に集中。実データ（rev179）は**逆行ゼロ** | ✅ 問題なし |

### 9.2 しかし「自分の履歴を再生しても元の状態に戻らない」

リプレイが成立する最低条件は「自分自身の履歴を再生したら元の `learning` に戻る」こと。
本物の `applyLearningResult` を通して測ったところ、**4場面中3場面で一致しなかった**。

| 場面 | 実際の状態 | 履歴から再生した状態 |
|---|---|---|
| **毎回、期限が来てから正解（普通の使い方）** | `stage=5` 次の復習 55日後 | **`stage=1` 次の復習 1日後** |
| 期限前に何度も解いた | `stage=1` | `stage=1`（一致） |
| 遅い正解が混ざる | `stage=2 streak=2` | `stage=1 streak=3` |
| 誤答をはさむ | `stage=1` 7日後 | `stage=0` 6日後 |

### 9.3 原因

`applyLearningResult`（28980行）は、**履歴に記録されていない入力**に依存する。

| 入力 | 役割 | 履歴にあるか |
|---|---|---|
| `srsDueAtStart` | **段階を進めるかどうかを直接決める**（`if (srsWasUnstarted \|\| srsDueAtStart) advanceSrs()`） | ❌ |
| `options.responseMs` | 遅い正解＝未定着の判定（`correctStreak` を1で頭打ち） | ❌ |
| `options.selfAssessment` | フラッシュカードの「あやふや」 | ❌ |
| `options.promptMode` | 仮習得の検証（`verifiesFlashcardMastery`） | ❌ |
| `adaptiveSrsEnabled()` | 間隔の伸縮。**端末ごとの設定で state にすら無い** | ❌ |

履歴は `{ at, correct }` しか持たない。よって段階の進み方を復元できない。

### 9.4 なぜこれが D2 より危険か

D2 は「時計がずれた端末と合流したとき」に起きる。リプレイ案の欠陥は
**合流のたびに全ユーザーの全単語で起きる**。普通の使い方の語が
55日間隔から1日間隔へ落ちるので、被害の規模が桁違いに大きい。

### 9.5 成立させるなら何が要るか（未着手）

履歴に `srsDueAtStart` と `responseMs`（少なくともこの2つ）を記録する必要がある。
その場合:

- 履歴は1語あたり最大50件あり、**単語データの大半を占める**。フィールド追加の
  サイズ影響を測る必要がある（§4.4 の `learning` への追加は解答済み1.2%の語にしか
  付かないので +0.3% で済んだが、履歴は事情が違う）
- **既存の履歴にはこれらの値が無い**。不明として扱う限り、既存データでは
  リプレイが正しく動かない。「ここより前は再生しない」という起点（チェックポイント）を
  別に持つ必要があり、そのチェックポイント自体をどう合流するかという問題が戻ってくる

## 10. ここまでで確定した制約（次の設計への引き継ぎ）

D2 を直す方法は、次の4つを**すべて**避ける必要がある。いずれも実測で否定済み。

| 使えないもの | 理由 | 根拠 |
|---|---|---|
| `stats` を因果の時計にする | `mergeWord` が履歴の和集合まで底上げする | 1.0.77 で撤回（前案） |
| 解答カウンタ1つ（スカラー） | 支配と並行を区別できず、相手の誤答を捨てる | §3 |
| 並行時に既存の保守的マージへ落とす | `srsStage: Math.min` で結局巻き戻る | 冒頭の検算 |
| `history` からのリプレイ | `srsDueAtStart` / `responseMs` が履歴に無い | §9 |

**残っている道**: 版数ベクトルで「支配か並行か」を判定するところまでは有効。
次に設計すべきは**並行と判定したときの合流規則**で、`min` でも `pick` でもなく、
「勝っている側の状態を起点に、相手だけが持つ解答を適用する」形が候補になる。
このとき適用するのは差分（通常1〜3件）だけなので、§9 のような全体のリセットは起きない。
ただし `srsDueAtStart` が不明である問題は差分にも残るため、**未検証**。

## 11. 差分適用マージの検証（2026-08-11・有望）

§10 で残った唯一の道「並行と判定したとき、進んでいる側を起点に、相手だけが持つ
解答を適用する」を実コードで検証した。**これまでの4案が落ちた関門をすべて通過した。**

### 11.1 srsDueAtStart は復元できる（§9 の壁を越えた）

§9 でリプレイ案が落ちた原因は `srsDueAtStart` が履歴に無いことだった。
しかしこのフラグの意味は「出題時点で復習期限が来ていたか」なので、
**答えた時刻とその時点の `nextReviewAt` を比べれば復元できる**:

```js
const due = Number(learning.nextReviewAt || 0) > 0 && answeredAt >= Number(learning.nextReviewAt);
```

実測（自分の履歴を再生して元の状態に戻るか）:

| 場面 | 素朴な再生（`due=false`） | **期限を復元した再生** |
|---|---|---|
| 毎回、期限が来てから正解（普通の使い方） | stage=1 / 1日後 ❌ | **stage=5 / 55日後 ✅ 完全一致** |
| 期限前に何度も解いた | ✅ 一致 | ✅ 一致 |
| 誤答をはさむ | stage=0 / 6日後 ❌ | **✅ 完全一致** |
| 遅い正解が混ざる | ❌ | ❌ `correctStreak` と1日ぶんの差 |

残る不一致は「遅い正解」だけ。`responseMs`（解答の速さ）は履歴に無いため復元できない。
ただし差は `4日 vs 5日`＝**出しすぎ側**で、既存の設計方針と同じ向き。

### 11.2 合流の規則

```
A ⊒ B（全成分で A ≧ B、かつ不一致あり） → A を丸ごと採用
B ⊒ A                                  → B を丸ごと採用
並行（支配関係なし）                      → 進んでいる側を起点に、
                                          相手だけが持つ解答を時刻順に適用する
```

起点の選び方は「ベクトルの合計が大きい側」。同数のときはベクトルの
文字列表現で決定的に決める（左右を入れ替えても同じ起点を選ぶため）。
適用するのは差分だけ（通常1〜3件）なので、§9 のような全体のリセットは起きない。

### 11.3 実測結果

| 場面 | 結果 |
|---|---|
| **(a) 時計ずれ**（Aが6回正解・時計55分遅れ / BはAを知らずに1回正解） | **stage=6 が保たれた**（現行は stage=1 へ巻き戻る）✅ |
| (b) 正当な降格（BがAの解答を全部持ったうえで誤答） | B が支配 → 降格が守られた ✅ |
| **(d) 並行 + 相手が誤答**（Aが5回正解 / BはAを知らずに1回誤答） | Aを起点にBの誤答を適用 → **`review` に落ちた**＝「忘れた」が守られた ✅（スカラー案が落ちた場面） |
| (c) 同数の並行 | 壊滅的な巻き戻りなし ✅ |

**可換性**: 全場面で `merge(A,B) === merge(B,A)` ✅
**収束**: 2端末の往復で **2往復目に固定点へ到達**し、以後は差分を出さない ✅
（1回目の失敗は「1往復目は通るが2往復目で元へ戻る」だった）

### 11.4 実装上の必須要件（検証中に発見）

**`learning.v` のキーは必ずソートして保持すること。**

`stateSignature`（19xxx行）は `JSON.stringify(state.words)` をそのまま使うため、
**オブジェクトのキーの並び順に依存する**。合流の左右でキー順が変わると
（`{devA:6,devB:1}` と `{devB:1,devA:6}` は中身が同じでも文字列が違う）、
両端末が「まだ差分がある」と誤認して**同期が止まらなくなる**。

既存コードが `deletions` を `Object.entries(...).sort(...)` で明示的にソートしているのと
同じ理由。`applyLearningResult` での加算時・`normalizeLearning` での正規化時・
合流時のすべてでソートする。

### 11.5 まだ検証していないこと（実装前に必要）

- **ランダム試行**（数千通りの解答列での巻き戻り・収束・可換性）
- **3台以上**での合流
- **旧版との混在**（片側に `v` が無い場合）が現行と同じ結果になること
- **性能**（9,701語での合流時間。差分適用は語ごとにループが増える）
- `responseMs` が復元できないことによる誤差が、**危険な向き（出さなすぎ）**へ
  倒れる経路が無いことの網羅的な確認

## 12. 残り検証の実施（2026-08-11・§11.5 をすべて消化）

§11.5 に残していた検証をローカルで一括実施した。ハーネスは本物の
`applyLearningResult` / `mergeLearningState` / `mergeHistory` を `publish/index.html`
から切り出して使用。乱数はシード固定（再現可能）。

### 12.1 追加で確定した設計要件

**(1) 支配判定は「ベクトル支配 AND 履歴キーの包含」にする。**
ベクトルは v を持つ端末の解答しか数えないため、ベクトルだけで勝者を丸ごと採用すると、
**旧版端末の解答（履歴にだけ居る）を黙って捨てる**。履歴の包含チェック（≤50件の
Set 照合）を支配の条件に加える。片方でも欠けたら並行扱い＝差分適用へ。

**(2) 履歴に `s` フラグ（遅い正解/あやふや）を追加し、再生時に尊重する。**
`s` が無いと遅い正解を普通の正解として再生し、段階を進めすぎる
（実測: 出さなすぎ459件・最大28.6日）。`s` はスキーマ版 1→2 と同時に導入する。
`normalizeHistory` / `mergeHistory` は現在 `{at, correct}` に作り直してフラグを
捨てるため、**両関数のフラグ保持対応が実装の必須要件**。旧クライアントはフラグを
剥がして保存するので、合流時はどちらかの複製が持っていれば残す（OR）。

**(3) `d` フラグ（期限到来）は記録しない。再生時は合流先の状態から導出する。**
記録した d を尊重する案も実測したが、**逆効果**（出さなすぎが最大59.9日へ悪化）。
期限到来かどうかは元の端末の文脈であり、別の状態に重ねると段階を進めすぎる。
`due = 答えた時刻 ≧ 合流先のその時点の nextReviewAt` の導出（§11.1）が正しい。

### 12.2 実測結果（ハイブリッド: s 尊重・d 導出）

  よる誤差（出しすぎ側優勢）に留まり、409 の壁で混在期は短い
