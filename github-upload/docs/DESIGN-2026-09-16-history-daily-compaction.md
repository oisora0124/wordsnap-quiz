# 学習履歴の日別畳み込み（historyDaily）

2026-09-16

## 背景

`word.history` は `{ at, correct }` の配列で、**1語あたり直近50件**しか残らない
（`foldHistoryIntoDaily` の切り詰め・以前は `normalizeHistory` / 採点直後 / `mergeHistory` の3か所）。
学習カレンダーと成績（`buildDailyActivity`）はこの `history` だけを日別に集計していたため、
50回を超えて解いた語の古い解答は、カレンダー・連続記録・最長連続から**消えていた**。

利用者の要望は「学習の記録を全て成績に残したい」。一方で生の履歴をすべて持つと、
語数 × 解答数ぶん容量が増え、同期の本文もそのまま膨らむ。
そこで **切り捨てる分を捨てずに、語ごとの日別カウントへ畳み込む**。

## データ形式

`word.historyDaily`（既存の語オブジェクトに1フィールド追加）:

```js
{
  days: { "YYYY-MM-DD": [解答数, 正解数], ... },  // UTC日付（at.slice(0, 10)）
  foldedThrough: "ISO時刻" | ""                  // この時刻以前は畳み込み済み（水位）
}
```

日キーは**UTC日付**で確定する。端末のローカル日付でキーを作ると、時差の違う端末が
同じ解答を別のキーへ積み、日ごとの max が効かずに二重計上され、以後どちらの端末でも
直せなくなる。表示側（`buildDailyActivity`）は「その日の 12:00Z」をローカル日付へ直して
カレンダーの日へ寄せる（±11時間までの時差なら同じ暦日に落ちる）。
そのため、**深夜に解いた分が前後1日ずれて表示されることがある**（回数の合計は変わらない）。
`days` のキーは常に日付順に作り直す。順序が端末ごとに違うと `stateSignature` が一致せず、
中身が同じでも接続のたびに全量PUTが走り続けるため。

- 1日1エントリ・数値2つ。上限 `HISTORY_DAILY_MAX_DAYS = 730`（超えたら古い日から落とす）。
- 生の `history` の形・50件上限（`HISTORY_RAW_MAX`）・`word.stats`・SRS・同期プロトコル・
  サーバーは一切変えていない。
- 旧データに `historyDaily` が無ければ空（`{ days: {}, foldedThrough: "" }`）から始まる。
  この機能より前に切り捨て済みの解答は復元できない（履歴自体が残っていないため）。

## 畳み込みと水位

`foldHistoryIntoDaily(history, daily)`（純関数・入力を変異させない）:

1. 履歴を正規化して時刻の昇順に並べる（`normalizeHistoryEntries`）。
2. 50件を超える分（＝古い側）を「落とす対象」にする。
3. 落とす対象のうち **`at > foldedThrough`** のものだけを `days[ローカル日付]` に加算する。
4. `foldedThrough` を「落とした対象の最大 at」と既存値の大きい方へ進める。
5. `{ history: 直近50件, historyDaily: 更新後 }` を返す。

水位を見るのは、**別端末で既に畳み込まれた解答を、同期で受け取った生の履歴から
二重に数えないため**。同じ入力を何度通しても増えない（冪等）。
履歴の切り詰めはこの関数だけが行うので、「捨てる解答は必ず日別に残る」ことが保証される。

呼び出し箇所は `normalizeWord`（読み込み・取り込み・同期の正規化）、採点直後（`gradeQuiz`）、
`mergeWord`（同期のマージ）の3か所。

## マージ規則

`mergeHistoryDaily(a, b)`: 日ごとに**解答数・正解数それぞれ max**、`foldedThrough` は max。
その後、`mergeHistoryEntries` で union した生の履歴を `foldHistoryIntoDaily` に通し、
あふれた分を「マージ済みの日別」へ水位より新しい分だけ畳み込む。

max を採るのは冪等性・収束性のため。加算にすると、同じ解答集合を両端末がそれぞれ
畳み込んでいた場合に同期のたびに回数が増え続ける（データが壊れて戻せない）。

### 限界（「全期間残す」が並行学習では部分的にしか成立しない）

- **本体の限界は水位 max による取りこぼし**。マージ後の水位は進んだ方にそろうため、
  相手端末だけが持っていた「統合後の水位以下の、まだ畳み込んでいない落とし分」は
  生の履歴からも日別からも消える。
  - 例: 端末Aが同じ日の 00:00 から1時間おきに60件、端末Bが 00:30 から1時間おきに60件を
    オフラインで解いた場合、マージ後に数えられるのは合計60（生50＋日別10）で、真値は120。
    `history-daily.test.mjs` に現状固定テストとして数値を残してある。
  - 旧実装（`slice(-50)`）でも同じ解答は捨てられていたので**退行ではない**が、
    「全期間を残す」は単一端末で学習している限りの保証だと理解する必要がある。
- 補助的な限界として、両端末が同じ日に別々に畳み込んだ分は**日ごとに max** を採るので、
  合計より少なくなり得る。増え続けて壊れるより、少なく見えて実害が小さい方を選んでいる。
- 水位の境界は `>` 判定なので、境界と同じミリ秒に記録された落とし分はすべて数えない
  （同じ語を同一ミリ秒に複数回採点した場合に限る）。

## 旧クライアントとの互換

- サーバー（`functions/api/wordsnap-state.js`）は word のフィールドを検証せず素通しするので、
  サーバー側で落ちることはない。
- **旧クライアントの `normalizeWord` は未知フィールドを保持しない**（返すオブジェクトを
  明示的に組み立てているため）。旧バージョンのアプリが同じ同期部屋の状態を読み書きすると、
  その端末が保存した word から `historyDaily` は消える。新クライアントは水位より前の
  解答を数え直さないので、**消えた日別は再畳み込みでは復元されない**。
  - 影響範囲はカレンダー・成績の「古い解答の回数」だけで、生の履歴・`stats`・SRS・
    連続記録（`streak.best` は保存値）には影響しない。
- サーバーには `HIGHEST_LEARNING_VERSION` による「古いスキーマでの上書きPUT」を弾く
  409 防御があるが、今回は仕様どおり `LEARNING_SCHEMA_VERSION` を据え置いた
  （同期プロトコル・サーバーは触らない）ため、この防御の対象にはならない。
  実際に損失が起きるのは「新版端末のローカルが無い状態で、旧版端末が先に押した」場合に限る。
  版上げでこの経路も塞ぐかは次サイクルの宿題。
- 逆に新クライアントが増えるだけなら、JSON バックアップ・復元（`normalizeWord` 経由）で
  そのまま保持される。単語帳の共有（`deckSharePayload`）は term/meaning/cefr/pos だけなので
  学習の記録は載らない（テストで固定）。CSV 書き出しの列も変えていない。

## 影響範囲の補足

`recentDailyAnswerCount`（復習の1日上限の推定）は `buildDailyActivity` を経由するので、
畳み込んだ分もこれまでより多く数えるようになる（推定が実態に近づく方向）。

## 容量見積

1日ぶんのエントリは `"2026-09-16":[12,7],` で約 25 バイト。
1語10日ぶんで約 250 バイト、1500語で約 375KB（上限の730日まで貯まっても、
日数は「その語で50件を超えて解いた日」だけなので現実的にはこれより遥かに小さい）。
生の履歴（1語50件で約 2KB）に比べれば増加は小さく、同期本文の桁は変わらない。
空のフィールド（`"historyDaily":{"days":{},"foldedThrough":""}`）自体は1語あたり約 44 バイトで、
`enrich` など既存の常在フィールドと同程度。1500語で約 66KB。
上限まで貯まった極値は1語730日で約 14.6KB、1500語で非圧縮 26MB となり、サーバーの
`MAX_INFLATED_JSON`（24MB）を超える。ただしこれは「1500語すべてを730日ぶん、毎日50回超
解いた」場合の値で、同期本文は gzip+base64（約 0.32MB）なので実運用では余裕がある。
