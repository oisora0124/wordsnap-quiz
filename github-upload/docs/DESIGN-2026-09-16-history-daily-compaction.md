# 学習履歴の日別記録（historyDaily）

2026-09-16

## 背景

`word.history` は `{ at, correct }` の配列で、**1語あたり直近50件**しか残らない
（切り詰めは `foldHistoryIntoDaily` の1か所に集約してある）。
学習カレンダーと成績（`buildDailyActivity`）はこの `history` だけを日別に集計していたため、
50回を超えて解いた語の古い解答は、カレンダー・連続記録・最長連続から**消えていた**。

利用者の要望は「学習の記録を全て成績に残したい」。一方で生の履歴をすべて持つと、
語数 × 解答数ぶん容量が増え、同期の本文もそのまま膨らむ。
そこで **切り捨てる分を捨てずに、語ごとの日別の記録へ畳み込む**。

### 初版（日ごとの [解答数, 正解数] ＋水位）をなぜ作り直したか

最初の実装は日ごとに `[解答数, 正解数]` の数を持ち、マージでは日ごとに **max**、
「どこまで畳み込んだか」の水位 `foldedThrough` も max を採っていた。
出荷前の第三者レビュー（Codex, high）で、**この合成が結合的でない**ことが分かった。

> 3端末 A・B・C が同じ語を同じ日にオフラインで60件ずつ解くと、
> `mergeWord(mergeWord(A,B),C)` は136件、`mergeWord(A,mergeWord(B,C))` は134件を返す（真値180）。

max は可換・冪等ではあるが結合的ではない。同期は「どの端末がどの順に相手と出会うか」を
決められないので、結合的でない合成は**端末ごとに違う値へ落ち着き、しかも真値と合わない**。
数（カウンタ）では和も max も救えない。救うには **1解答を区別できる識別子にして、
合成を集合の和にする**しかない。データ形式は出荷後に変えにくいので、出荷前に作り直した。

## データ形式

`word.historyDaily`（既存の語オブジェクトに1フィールド追加）:

```js
{
  days: {
    "YYYY-MM-DD": "<token>,<token>,...",  // UTC日付 → その日の解答トークン列
    ...
  }
}
```

- **token** = `その日の秒(0〜86399)を36進` + `("+" 正解 / "-" 誤答)。` 例: `"1k3+,2ab-"`
- 1トークン＝1解答。同一性は **(UTC日, その日の秒, 正誤)** で決まる。
- 日の中のトークンは**秒の昇順・重複なし**に正規化して保存する。日キーもソートする。
  並びが端末ごとに違うと `stateSignature` が一致せず、中身が同じでも接続のたびに
  全量PUTが走り続けるため、保存する形をここで一意に決めている。
- 上限は **`HISTORY_DAILY_MAX_ENTRIES = 3000`（語ごとの総トークン数）**。
  超えたら古い日から**丸ごと**落とす（日の途中で切ると、その日の件数が端末間で
  食い違って和が壊れるため）。1日だけで上限を超える語でも最後の1日は残す。
- 水位（`foldedThrough`）は**持たない**。集合の和は何度足しても増えないので、
  「どこまで畳み込んだか」を覚える必要がそもそも無い。
- 生の `history` の形・50件上限（`HISTORY_RAW_MAX`）・`word.stats`・SRS・
  同期プロトコル・サーバーは一切変えていない。

日キーを**UTC日付**で確定するのは、端末のローカル日付でキーを作ると、時差の違う端末が
同じ解答を別のキーへ積み、和を採っても二重に数えてしまうため。表示側（`buildDailyActivity`）は
「その日の 12:00Z」をローカル日付へ直してカレンダーの日へ寄せる
（±11時間までの時差なら同じ暦日に落ちる）。そのため、**深夜に解いた分が前後1日ずれて
表示されることがある**（回数の合計は変わらない）。

## 演算（すべて純関数・入力を変異させない）

### `foldHistoryIntoDaily(history, daily)`

1. 履歴を正規化して時刻の昇順に並べる（`normalizeHistoryEntries`）。
2. 50件を超える分（＝古い側）を「落とす対象」にする。
3. 落とす対象を `historyDailyTokenFor` でトークン化し、`days[UTC日付]` の集合へ**足す**。
4. 触った日だけ重複排除・整列し、総件数の上限で古い日を落とす。
5. `{ history: 直近50件, historyDaily: 更新後 }` を返す。

同じ履歴を何度通しても結果は変わらない（**冪等**）。集合への追加なので、水位のような
状態を持たずに二重計上を防げる。履歴の切り詰めはこの関数だけが行うので、
**「生から落ちる解答は必ず日別に入る」**ことが保証される。
呼び出し箇所は `normalizeWord`（読み込み・取り込み・同期の正規化）、採点直後（`gradeQuiz`）、
`mergeWord`（同期のマージ）の3か所。

### `mergeHistoryDaily(a, b)`

日ごとに**トークン集合の和**を採るだけ。和は **可換・結合・冪等**なので、
何台の端末をどの順に突き合わせても同じ値へ収束する。
（`{x} ∪ {y} = {y} ∪ {x}`、`({x}∪{y})∪{z} = {x}∪({y}∪{z})`、`{x}∪{x} = {x}`。）

### `mergeWord`

生の履歴の和集合（`mergeHistoryEntries`）→ 日別の和（`mergeHistoryDaily`）→ `foldHistoryIntoDaily`。

`生 ∪ 日別` は「両端末が持っていた解答の和」に等しく、`生` は常にその和の新しい50件、
`日別` はその残り、と一意に決まる。だから **`(A⊔B)⊔C` と `A⊔(B⊔C)` が一致し、
値も真値と合う**（上の3端末×60件の例で180件）。`check-release.mjs` と
`history-daily.test.mjs` の両方で、順番を入れ替えた結果の一致と合計180を固定している。

### `normalizeHistoryDaily(daily)`

- 日キーは正規表現に加えて `Date.UTC` で往復検証する。`2026-02-31` は正規表現を通るが
  実在しない日で、表示側の `Date` が別の日へ繰り上がってカレンダーがずれるため。
- トークンは `^[0-9a-z]{1,4}[+-]$` かつ秒 < 86400 のものだけ残す。
- 値が文字列でないもの（**旧フォーマットの `[解答数, 正解数]` を含む**）は捨てる。
  旧フォーマットは本番未リリースなので、変換せず捨てる方が単純で安全。
  廃止した `foldedThrough` は読み捨て、保存もしない。

### `buildDailyActivity(words)`

生の履歴（ローカル日）に加え、日別の各日について
`answers = トークン数`、`correct = "+" の数` を足し、その日の `terms` にその語を加える。
UTC日キーは 12:00Z 経由でローカル日へ寄せる。

## 限界（正直に書く）

- **同一秒・同一正誤の解答は1件に畳まれる。** 同一性を (日, 秒, 正誤) にしたことの代償で、
  1語を同じ秒に2回採点した場合にだけ起きる。旧実装が同一ミリ秒を1件と見ていたのと同種の
  限界で、ミリ秒まで持つと1トークンが約3バイト太る割に、人間の解答間隔では意味が無い。
- **上限に達した語では結合性が崩れる。** 総件数が 3000 を超えると古い日を落とすため、
  「落としてから足す」か「足してから落とす」かで結果が変わりうる。上限のある集合では
  避けられない性質で、3000件（≒その語だけで3000回の超過解答）に達する語は実質無い。
- **旧クライアントが同じ部屋に混ざると日別が消える**（次節）。
- カレンダーの日付は UTC→12:00Z→ローカルの丸めなので、深夜の解答は前後1日ずれうる。

## 旧クライアントとの互換

- サーバー（`functions/api/wordsnap-state.js`）は word のフィールドを検証せず素通しするので、
  サーバー側で落ちることはない。
- **旧クライアントの `normalizeWord` は未知フィールドを保持しない**（返すオブジェクトを
  明示的に組み立てているため）。旧バージョンのアプリが同じ同期部屋の状態を読み書きすると、
  その端末が保存した word から `historyDaily` は消える。生の履歴に残っていない解答は
  再畳み込みでは復元できないので、**消えた日別はそのまま失われる**。
  - 影響範囲はカレンダー・成績の「古い解答の回数」だけで、生の履歴・`stats`・SRS・
    連続記録（`streak.best` は保存値）には影響しない。
- サーバーには `HIGHEST_LEARNING_VERSION` による「古いスキーマでの上書きPUT」を弾く
  409 防御があるが、今回は仕様どおり `LEARNING_SCHEMA_VERSION` を据え置いた
  （同期プロトコル・サーバーは触らない）ため、この防御の対象にはならない。
  実際に損失が起きるのは「新版端末のローカルが無い状態で、旧版端末が先に押した」場合に限る。
- **サーバー側で `historyDaily` の形を検証する（壊れた形の混入を止める）のは次サイクルの宿題。**
  現状はクライアントの `normalizeHistoryDaily` が受信時に必ず通るので、壊れた値が
  カレンダーへ出ることはないが、部屋の中に壊れた値が居座ることは止められない。
- 新クライアントどうしなら、JSON バックアップ・復元（`normalizeWord` 経由）でそのまま
  保持される。単語帳の共有（`deckSharePayload`）は term/meaning/cefr/pos だけなので
  学習の記録は載らない（テストで固定）。CSV 書き出しの列も変えていない。

## 影響範囲の補足

`recentDailyAnswerCount`（復習の1日上限の推定）は `buildDailyActivity` を経由するので、
畳み込んだ分もこれまでより多く数えるようになる（直近7日の中央値なので、影響が出るのは
「7日以内に1語で50件を超えて解いた」場合だけ。推定が実態に近づく方向）。

`undoSignature` にも `historyDaily` を含めた（`stateSignature` と範囲をそろえた）。
含めないと、日別だけが増えたリモート状態を取り込んだ直後に「変更なし」と判定され、
直前の操作のUndoが残り続けて、押すと日別の記録まで巻き戻ってしまう。

## 容量見積

- 1トークンは平均 約5.5バイト（秒の36進が3〜4文字＋正誤1文字＋区切りのカンマ）。
- 日キーは1日あたり 約16バイト（`"2026-09-16":"...",`）。
- **1語の上限**（3000トークン・30日ぶん）で 約16KB。
- **空のフィールド** `"historyDaily":{"days":{}}` は1語あたり 28バイト。
  1500語で 約42KB と、実質ゼロ。
- **現実的な値**: 1語で50件を超えて解く語はそもそも少なく、そういう語でも
  1日あたり数件・数十日ぶん。1語 約1KB、1500語のうち1割が該当して 約150KB。
  生の履歴（1語50件で 約2KB、1500語で 約3MB）に比べれば桁違いに小さい。
- **極値**: 1500語すべてが上限まで貯まると非圧縮で 約25MB となり、サーバーの
  `MAX_INFLATED_JSON`（24,000,000バイト）に触れる。ただしこれは 1語3000回 × 1500語＝
  **450万解答**という到達不能な量（1解答5秒でも6000時間超）で、そこに至るより前に
  生の履歴・語数の側で容量の壁に当たる。実測では gzip で 約12MB まで縮む（同期本文は
  gzip+base64）。将来ここが現実味を帯びたら、上限を下げる（`HISTORY_DAILY_MAX_ENTRIES`
  を変えるだけで形式は変わらない）か、サーバー側で語ごとに切ることで対処できる。
