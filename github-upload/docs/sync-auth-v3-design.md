# 同期認証V3（capability分離）— 検討記録・不採用

**状態: 不採用（2026-07-26）。** 実装しない。将来やるなら本書を出発点にする。

一度は設計まで書いて着手直前まで進めたが、Advisorレビューで前提の誤りが3つ見つかり、
**やっても目的を達成できない**ことが分かったので取り下げた。同じ検討を繰り返さないための記録。

## 1. 何をやろうとしたか

`x-room-key` でサーバーへ送る値を、room secret（`wk_…`）そのものではなく、
そこから HKDF 派生した capability（`wc_…`）に変える。secret がサーバーへ届かなくなるので、
secret から派生する封筒の鍵（AIキー暗号化同期）も導けなくなる、という筋書きだった。

移行は `updateAuthHashLazily()` の遅延方式を流用し、`rooms.auth_wire` で
どちらの値でハッシュしたかを覚え、二段階（両方受理 → cap専用）で切り替える計画だった。

## 2. なぜ取り下げたか

### 2.1 同一オリジンのPWAでは、運営を脅威モデルに入れられない（決定的）

WordBank はアプリ本体（HTML）も `/api/*` も同じオリジンから運営が配信している。
運営はユーザーのブラウザで任意のコードを実行できる立場にあり、
**封筒を復号するまでもなく、localStorage の平文APIキーを直接読める**。

暗号をどれだけ正しく作っても、この事実は変わらない。CSPもSRIも同じ配信物の一部なので
根拠にならない。つまり「**運営も読めません**」という表示は、この構成である限り
どんな認証方式でも成立しない。

これを本当に解くには、運営とは独立に配布・検証できるクライアント（拡張機能、署名付き
ネイティブアプリ、第三者が検証できる不変ビルド）が要る。認証の話ではない。

### 2.2 締め出し対策として書いた403フォールバックが、そのまま裏口だった

設計3.1に「cap だけで 403 が返ったら、1回だけ secret 併用へ戻して再試行する」と書いた。
旧クライアントを締め出さないための安全装置のつもりだったが、これは
**悪意ある運用者が403を返すだけで secret を引き出せるプロトコル**である。
防ごうとしていた相手に鍵を渡す経路を、対策として自分で設計していた。

削除すれば裏口は塞がるが、今度は締め出し対策が無くなる。
**秘匿性と「誰も締め出さない」は自動では両立しない**——両立させるにはユーザーの明示操作を
伴う移行が要る、というのがこの検討で得た本質的な結論。

### 2.3 既存の部屋は、認証を変えても救われない

過去のV2リクエストを一度でも記録していれば `wk_` は永久に有効で、
そこから派生する封筒の鍵も永久に導ける。認証を今日から変えても、
**既に流出した可能性のある鍵素材は取り消せない**。

既存の部屋を本当に安全にするには、サーバーを一度も通っていない新しい鍵素材へ
張り替える（rekey）しかない。そしてその新しい鍵素材の配布経路は、結局
**引き継ぎコード**になる。

## 3. 結論と、実際に採った方針

2.3 から、V3認証をやっても**結局は引き継ぎコードに新しい鍵素材を載せることになる**。
ならば最初からそれをやるほうが、目的を直接かつ完全に達成し、稼働中の認証にも触れず、
締め出しリスクもゼロになる。

そこで採用したのが **vault key 方式**（`docs/ai-secret-sync-design.md`）:

- 封筒の鍵は、端末で生成しサーバーへ一度も送らない乱数（`wv_…`）から派生する
- 認証は `wk_…` のまま**一切変更しない**
- 引き継ぎコードを `wr_….wk_….wv_…` の3要素へ拡張する

## 4. それでもV3認証に残る価値（将来やるなら）

vault key 方式を入れても、次の価値は残る。独立した硬化項目として、必要になったら着手する。

- リクエストログ・WAF・中間層・トレースに、部屋の全権限を持つ bearer が残らなくなる
- `wk_` が漏れると部屋の単語データを全て読み書きできる。これは封筒の鍵とは別の問題で、
  vault key 方式では解決しない

着手するなら、本書1章の方式に加えて、レビューで挙がった以下を必ず設計へ織り込むこと:

- 403フォールバックは**作らない**（2.2）。旧クライアント対策はユーザーの明示操作で行う
- 移行時、サーバーは `wk_` から期待 cap を派生して定時間比較し、一致しなければDBを変えない
- 切り戻し用に `auth_hash_prev` / `auth_kid_prev`（いずれもnullable）を持ち、単一CASで更新する
- 鍵リングのローテーションと移行が同時に起きても primary=cap / prev=secret が保たれること
- `op=upgrade`（legacy→V2）も cap で部屋を作る経路に含める
- `wc_` を telemetry・ログ・診断のredaction対象へ追加する
- 「全部屋 `auth_wire='cap'`」だけを cap専用化の条件にしない。オフライン端末・長時間開いた
  旧タブが残る
- マイグレーション適用 → 旧Function疎通確認 → 新Function配信、の順序を固定する
